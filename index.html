01Explain the four OOP principles — with examples from your framework, not from a textbook›
  • Abstraction — the test says loginPage.loginAs(user, pass). It has no idea a WebDriver exists. The what is exposed, the how is hidden.
  • Encapsulation — inside LoginPage, the locators are private final By. Nothing outside the page class can touch an element directly, so a UI change is a one-file change.
  • Inheritance — every page extends BasePage, which owns the driver, the wait, and the shared click()/type() helpers. Written once, used everywhere.
  • Polymorphism — WebDriver driver = factory.create("firefox"). Same reference type, different runtime object. That's runtime polymorphism. Overloading click(By) and click(WebElement) is compile-time polymorphism.
Follow-up they will askWhich of those is decided at compile time and which at runtime? Overloading = compile time (the compiler picks by signature). Overriding = runtime (the JVM picks by actual object type).
02Why is String immutable, and why does it matter?›

Once a String object is created its contents can never change — every "modification" returns a brand-new object. Four reasons it's designed that way:

  • The string pool — identical literals can safely share one object, because nobody can mutate it out from under anyone else.
  • Safe HashMap keys — the hashCode is computed once and cached. If a String could change, a key would get lost in its own map.
  • Thread safety — immutable objects are automatically safe to share across threads with no locking.
  • Security — usernames, URLs and connection strings can't be altered after a security check has passed.
Follow-up"So what do you use in a loop?" — StringBuilder. Concatenating with + inside a loop creates a new String and a new StringBuilder on every iteration. Building a dynamic XPath over 200 grid rows is exactly where this shows up.

04== vs equals() vs hashCode() — and the contract between them›

== compares references for objects (do both variables point at the same object in memory) and values for primitives. equals() compares content, provided the class overrides it — the default Object.equals() is just ==.

The contract, in one line: equal objects must produce equal hashCodes. The reverse is not required — two unequal objects may collide on the same hashCode.

Say this"If I override equals() and forget hashCode(), my object goes into a HashSet and then contains() returns false for an object that is equal — because the lookup goes to the wrong bucket. It fails silently, which is the worst kind of failure."
Follow-upWhy does Integer a=127, b=127; a==b return true but 128 return false? Integer caches boxed values from −128 to 127, so the small ones are the same object. Never compare wrapper objects with ==.
05Abstract class vs interface — which would you use in a framework?›
  • Abstract class — can hold state (fields), constructors and concrete methods. A class can extend only one. Use it for BasePage, which genuinely holds a driver and a wait that every page shares.
  • Interface — a contract. A class can implement many. Since Java 8 it can have default and static methods; since Java 9, private methods too. Use it for pluggable capability: IRetryAnalyzer, ITestListener, a custom Reportable.

Rule of thumb: an abstract class models "is a kind of"; an interface models "is able to."

Follow-up"Can an interface have a constructor?" No — it has no state to initialise and is never instantiated directly.
06Overloading vs overriding — and the rules for overriding›

Overloading: same method name, different parameter list, same class. Resolved by the compiler. Return type alone is not enough to overload.

Overriding: subclass redefines a superclass method. Resolved at runtime. The rules:

  • Identical name and parameter list
  • Return type same, or a subtype (covariant return)
  • Access cannot be narrowed — public stays public
  • Cannot throw broader checked exceptions than the parent
  • static, final and private methods can't be overridden (a static one is hidden, not overridden)
07Walk me through the exception hierarchy — and where do Selenium's exceptions sit?›

Throwable splits into Error (JVM-level, don't catch — OutOfMemoryError, StackOverflowError) and Exception. Exception splits into checked (IOException, SQLException — compiler forces handling) and RuntimeException, which is unchecked (NullPointer, ArrayIndexOutOfBounds, IllegalArgument).

Every Selenium exception extends WebDriverException, which extends RuntimeException. That is why you never have to wrap findElement in a try/catch — it's unchecked by design, so the test simply fails, which is the behaviour you want.

Follow-up"Does finally always run?" Almost always — it's skipped only on System.exit() or a JVM crash. And a return inside finally overrides the one in try, which is a classic trick question.
08final vs finally vs finalize›
  • final — a keyword. A final variable can't be reassigned, a final method can't be overridden, a final class can't be extended.
  • finally — a block that runs whether or not an exception was thrown. Where driver.quit() used to live before try-with-resources.
  • finalize() — a legacy Object method the GC could call before collecting. Deprecated since Java 9, removed in practice. Never rely on it.
09Explain the Collections hierarchy›

Collection is the root interface for List, Set and Queue. Map is not a Collection — it's a separate hierarchy of key→value pairs.

ArrayList vs LinkedList: ArrayList is a resizable array — O(1) random access, but inserting in the middle shifts everything. LinkedList is a doubly-linked node chain — O(1) insert/remove once you're at the node, but O(n) to get there. In test automation it's ArrayList 95% of the time.

10How does HashMap work internally?›

A HashMap is an array of buckets. On put(k,v):

  • It calls k.hashCode(), then applies its own spreading function (XORs the high bits down) so poor hash functions don't all land in the same bucket.
  • That value is masked to an index in the bucket array.
  • If the bucket is empty, the entry goes in. If not — a collision — it walks the existing entries comparing with equals(). Same key → value replaced; different key → appended.

The numbers they want to hear: default capacity 16, load factor 0.75, so it resizes (doubles and rehashes) at 12 entries. A bucket whose chain reaches 8 entries converts from a linked list to a red-black tree — dropping worst-case lookup from O(n) to O(log n) — and reverts at 6. Treeifying only happens once the table is at least 64 buckets; below that it just resizes instead.

Follow-up"What if two different keys have the same hashCode?" They land in the same bucket and are separated by equals(). That's exactly why the equals/hashCode contract exists.

12What is ConcurrentModificationException, and fail-fast vs fail-safe?›

Collections like ArrayList and HashMap keep a modCount. Their iterators snapshot it at creation and check it on every next(). Structurally modify the collection while iterating and the check fails → ConcurrentModificationException. That's fail-fast: it surfaces the bug immediately rather than corrupting data silently.

Fail-safe iterators (CopyOnWriteArrayList, ConcurrentHashMap) iterate over a snapshot or tolerate concurrent writes, so they never throw — but you may not see the newest elements.

Three legal ways to remove while looping: iterator.remove(), list.removeIf(predicate), or iterate a copy and mutate the original.

13Which Java 8 features do you actually use in automation?›
  • Lambdas + functional interfaces — ExpectedCondition is a functional interface, which is why wait.until(d -> d.findElements(by).size() > 3) compiles. That's a great thing to point out; it shows she understands why the API works, not just how to call it.
  • Stream API — extracting and asserting on grid data without a for-loop.
  • Optional — modelling "element may not be there" without returning null.
  • default methods — how interfaces evolved without breaking every implementer.
  • Method references — WebElement::getText.
  • java.time — and Selenium 4's Duration.ofSeconds() in every timeout.

A concrete example worth memorising — asserting a price column is sorted:

14Intermediate vs terminal stream operations›

Intermediate operations return another Stream and are lazy — filter, map, sorted, distinct, limit, peek. Nothing runs until a terminal operation arrives.

Terminal operations produce a result and consume the stream — collect, forEach, count, reduce, anyMatch, findFirst. A stream can only be consumed once; reusing it throws IllegalStateException.

Follow-up"What does a stream with only filter and no terminal op print?" Nothing at all. Laziness means the pipeline never executes.
15What does static mean — and why is a static WebDriver a bug?›

static members belong to the class, not to any instance — one copy shared by everything, loaded when the class loads. Static methods can't use this and can't access instance members directly.

Which is exactly the problem: public static WebDriver driver; means one driver shared by every thread. Run with parallel="methods" and thread B overwrites the field while thread A is mid-test — you get random NoSuchWindowException and impossible-looking failures. The fix is ThreadLocal<WebDriver>: one value per thread, same static access pattern.

Say this"I'd keep the factory static but never the driver itself — the driver goes in a ThreadLocal, and I call remove() in the teardown so the thread pool doesn't leak sessions between tests."

17Threads, ExecutorService and ThreadLocal — the lead-level slice›
  • Thread / Runnable — implement Runnable rather than extend Thread, because Java allows only one superclass.
  • ExecutorService — a managed thread pool; you submit tasks instead of creating threads. TestNG's parallel execution is doing this for you under the hood.
  • synchronized — a lock around a critical section; correct but coarse.
  • ThreadLocal — a per-thread variable. The right tool for WebDriver, ExtentTest and test-data context in a parallel suite. Always remove() in teardown or a pooled thread keeps the stale value.

01

Reverse a string without using StringBuilder.reverse()

They add the restriction precisely because reverse() is the answer everyone gives.

Show solution
public static String reverse(String input) {
    if (input == null) return null;

    char[] chars = input.toCharArray();

    // Two pointers. left walks forward, right walks backward,
    // and they swap until they meet in the middle.
    for (int left = 0, right = chars.length - 1; left < right; left++, right--) {
        char temp    = chars[left];
        chars[left]  = chars[right];
        chars[right] = temp;
    }
    return new String(chars);
}
O(n) time · O(n) space · two-pointer swap, in place on the char array

Why a for loop and not a while: a for declares both pointers, the stop condition and both moves on one line, so you can read the whole loop at a glance. Writing chars[left++] = chars[right] inside a while hides the movement inside the assignment — it works, but it's the kind of line that's easy to get wrong under pressure on a whiteboard. Keep the swap and the movement separate.

Follow-up: "Do it recursively." — return reverse(s.substring(1)) + s.charAt(0); with if (s.isEmpty()) return s; as the base case. Then say the honest thing: it's elegant but allocates a new String per frame and stack-overflows on long input, so the iterative version is what she'd ship.

Another way to say it

If they don’t ban it — ask first, then say this:

return new StringBuilder(input).reverse().toString();

Recursive — elegant, but it allocates a String per frame and overflows the stack on long input:

public static String reverse(String s) {
    if (s == null || s.length() <= 1) return s;
    return reverse(s.substring(1)) + s.charAt(0);
}
Lead withThe two-pointer for loop. The question almost always bans reverse(), and the loop shows you can manipulate an array. Mention the other two as alternatives — that is what turns a correct answer into a confident one.
02

Check whether a string is a palindrome

"A man, a plan, a canal: Panama" should return true. That's the real version of this question.

Show solution
public static boolean isPalindrome(String input) {
    if (input == null) return false;

    String clean = input.replaceAll("[^A-Za-z0-9]", "").toLowerCase();

    for (int left = 0, right = clean.length() - 1; left < right; left++, right--) {
        if (clean.charAt(left) != clean.charAt(right)) {
            return false;
        }
    }
    return true;
}
O(n) time · O(n) space for the cleaned copy

The mark is in the cleanup. Most candidates compare raw characters and fail on spaces and punctuation. Stripping non-alphanumerics and lower-casing first, unprompted, is what separates the answers.

Another way to say it

Reverse and compare — the shortest thing to say out loud:

String clean = s.replaceAll("[^A-Za-z0-9]", "").toLowerCase();
return clean.equals(new StringBuilder(clean).reverse().toString());
Lead withThe two-pointer loop — it allocates no second string and exits on the first mismatch. Then add: “or in one line, reverse it and compare, but that builds a whole extra string.” Naming the trade-off is the part that scores.
03

Count how many times each character appears

Input "automation" → {a=2, u=1, t=2, o=2, m=1, i=1, n=1}

Show solution
public static Map<Character, Integer> frequency(String input) {
    Map<Character, Integer> counts = new LinkedHashMap<>();

    for (char c : input.toCharArray()) {
        counts.put(c, counts.getOrDefault(c, 0) + 1);
    }
    return counts;
}

Java 8 version — worth writing both, then saying which she'd use:

Map<Character, Long> counts = input.chars()
        .mapToObj(c -> (char) c)
        .collect(Collectors.groupingBy(c -> c, LinkedHashMap::new, Collectors.counting()));

Why LinkedHashMap and not HashMap: insertion order is preserved, so the output reads in the order the characters appeared. With a plain HashMap the order is unpredictable — and program 04 depends on that order being correct.

04

Find the first non-repeating character

Input "swiss" → w. The classic follow-up to program 03.

Show solution
public static Character firstNonRepeating(String input) {
    Map<Character, Integer> counts = new LinkedHashMap<>();

    for (char c : input.toCharArray()) {
        counts.put(c, counts.getOrDefault(c, 0) + 1);
    }

    for (Map.Entry<Character, Integer> entry : counts.entrySet()) {
        if (entry.getValue() == 1) {
            return entry.getKey();
        }
    }
    return null;   // every character repeats
}

Stream version:

return counts.entrySet().stream()
        .filter(e -> e.getValue() == 1)
        .map(Map.Entry::getKey)
        .findFirst()
        .orElse(null);

Follow-up: "Why two passes?" Because you can't know a character is unique until you've seen the whole string. Two O(n) passes is still O(n) — say that, because interviewers ask it to see if she'll panic and invent a worse one-pass answer.

05

Check whether two strings are anagrams

"listen" and "silent" → true

Show solution
public static boolean isAnagram(String first, String second) {
    if (first == null || second == null) return false;

    char[] a = first.replaceAll("\\s", "").toLowerCase().toCharArray();
    char[] b = second.replaceAll("\\s", "").toLowerCase().toCharArray();

    if (a.length != b.length) return false;   // cheap exit first

    Arrays.sort(a);
    Arrays.sort(b);

    return Arrays.equals(a, b);
}
O(n log n) because of the sort

Follow-up: "Can you do it in O(n)?" Yes — count characters into a map (or an int[26] for pure lowercase letters), incrementing for the first string and decrementing for the second. If every count ends at zero, they're anagrams.

Another way to say it

O(n) counting — this is the follow-up they ask for, so have it ready:

public static boolean isAnagram(String a, String b) {
    String x = a.replaceAll("\\s", "").toLowerCase();
    String y = b.replaceAll("\\s", "").toLowerCase();
    if (x.length() != y.length()) return false;

    int[] counts = new int[26];
    for (int i = 0; i < x.length(); i++) {
        counts[x.charAt(i) - 'a']++;
        counts[y.charAt(i) - 'a']--;
    }

    for (int c : counts) {
        if (c != 0) return false;
    }
    return true;
}

The int[26] only works for plain a–z. For unicode, count into a Map<Character, Integer> the same way.

Lead withThe sort-and-compare version — four lines and obviously correct. Then say “that is O(n log n) because of the sort; if you want O(n) I would count characters instead” and write the second one. Offering the upgrade unprompted is the whole game here.
06

Reverse each word, keeping word order

"Selenium with Java" → "muinaleS htiw avaJ"

Show solution
public static String reverseEachWord(String sentence) {
    String[] words = sentence.trim().split("\\s+");
    StringBuilder result = new StringBuilder();

    for (String word : words) {
        result.append(new StringBuilder(word).reverse()).append(" ");
    }
    return result.toString().trim();
}

The variant they ask next — reverse the word order instead:

public static String reverseWordOrder(String sentence) {
    String[] words = sentence.trim().split("\\s+");
    Collections.reverse(Arrays.asList(words));   // reverses the backing array
    return String.join(" ", words);
}

Note split("\\s+"), not split(" ") — the regex collapses multiple spaces, so double spaces don't produce empty words.

07

Remove duplicate characters, preserving order

"programming" → "progamin"

Show solution
public static String removeDuplicateChars(String input) {
    StringBuilder result = new StringBuilder();
    Set<Character> seen = new HashSet<>();

    for (char c : input.toCharArray()) {
        if (seen.add(c)) {        // add() returns false if already present
            result.append(c);
        }
    }
    return result.toString();
}

The detail worth saying out loud: Set.add() returns a boolean, so the check and the insert happen in one operation. Most candidates write if (!seen.contains(c)) { seen.add(c); ... }, which works but does the lookup twice.

Another way to say it

Stream version:

return input.chars()
        .distinct()
        .mapToObj(c -> String.valueOf((char) c))
        .collect(Collectors.joining());

LinkedHashSet — same idea, more obvious:

Set<Character> unique = new LinkedHashSet<>();
for (char c : input.toCharArray()) {
    unique.add(c);
}

StringBuilder result = new StringBuilder();
for (char c : unique) {
    result.append(c);

public static void analyse(String sentence) {

Find the second largest element in an array

Without sorting. This one comes up constantly.

Show solution
public static int secondLargest(int[] numbers) {
    if (numbers == null || numbers.length < 2) {
        throw new IllegalArgumentException("Need at least two elements");
    }

    int largest = Integer.MIN_VALUE;
    int second  = Integer.MIN_VALUE;

    for (int n : numbers) {
        if (n > largest) {
            second = largest;
            largest = n;
        } else if (n > second && n != largest) {
            second = n;
        }
    }

    if (second == Integer.MIN_VALUE) {
        throw new IllegalArgumentException("All elements are identical");
    }
    return second;
}
O(n) time · O(1) space · single pass, no sort

Stream version, if they allow it:

int second = Arrays.stream(numbers)
        .distinct()
        .boxed()
        .sorted(Comparator.reverseOrder())
        .skip(1)
        .findFirst()
        .orElseThrow(() -> new IllegalArgumentException("No distinct second largest"));

The edge case they're testing: {5, 5, 5}. Without the n != largest check, the answer comes back as 5, which is wrong. Volunteer that case before they raise it.

    Set<Integer> duplicates = new LinkedHashSet<>();

        if (!seen.add(n)) {      // add() failed, so we've seen it before
            duplicates.add(n);
        }
    }
    return duplicates;
}
O(n) time · O(n) space · beats the nested-loop O(n²) answer

}
Lead withThe two-Set version — O(n), and the !seen.add(n) idiom reads well. Mention sort-and-scan as your answer if they say “no extra space”.
12

Find the missing number in an array of 1 to n

{1, 2, 4, 5} with n = 5 → 3

Show solution
public static int missingNumber(int[] numbers, int n) {
    int expectedSum = n * (n + 1) / 2;

    int actualSum = 0;
    for (int x : numbers) {
        actualSum += x;
    }
    return expectedSum - actualSum;
}
O(n) time · O(1) space · no sorting, no extra collection

Follow-up: "What if n is large enough to overflow?" Use long for the sums, or XOR every index with every value — the pairs cancel out and the missing number survives, with no overflow risk at all.

Another way to say it

XOR — no overflow risk at all, which is exactly the follow-up they ask:

public static int missingNumber(int[] numbers, int n) {
    int xor = 0;

    for (int i = 1; i <= n; i++) {
        xor ^= i;            // XOR of every expected value
    }
    for (int value : numbers) {
        xor ^= value;        // pairs cancel out, the missing one survives
    }
    return xor;
}

Presence array — the most obvious version, if the maths deserts you:

boolean[] present = new boolean[n + 1];
for (int value : numbers) {
    present[value] = true;
}

for (int i = 1; i <= n; i++) {
    if (!present[i]) return i;
}
return -1;
Lead withThe sum formula — one line, obviously O(n) time and O(1) space. Then volunteer: “for a large n I would use long for the sums, or XOR, which cannot overflow at all.”

Sort an array without using Arrays.sort()

Bubble sort is fine — just include the optimisation.

Show solution
public static void bubbleSort(int[] arr) {
    for (int i = 0; i < arr.length - 1; i++) {
        boolean swapped = false;

        for (int j = 0; j < arr.length - 1 - i; j++) {
            if (arr[j] > arr[j + 1]) {
                int temp = arr[j];
                arr[j] = arr[j + 1];
                arr[j + 1] = temp;
                swapped = true;
            }
        }

        if (!swapped) break;   // already sorted, stop early
    }
}
O(n²) worst case · O(n) on already-sorted input thanks to the flag

Two details interviewers look for: the inner loop bound is length - 1 - i (the tail is already sorted after each pass), and the swapped flag. Without either it still works, but it signals she reproduced it from memory rather than understood it.

Another way to say it

Selection sort — fewer swaps, same complexity:

for (int i = 0; i < arr.length - 1; i++) {
    int minIndex = i;

    for (int j = i + 1; j < arr.length; j++) {
        if (arr[j] < arr[minIndex]) {
            minIndex = j;
        }
    }

    int temp = arr[minIndex];
    arr[minIndex] = arr[i];
    arr[i] = temp;
}

Insertion sort — O(n) on nearly-sorted data, which is the interesting thing to say about it:

for (int i = 1; i < arr.length; i++) {
    int key = arr[i];
    int j = i - 1;

    for (; j >= 0 && arr[j] > key; j--) {
        arr[j + 1] = arr[j];
    }
    arr[j + 1] = key;
}
Lead withBubble sort with the swapped flag — it is what they expect, and the flag shows you understood it rather than memorised it. Knowing a second one by name, with a reason to prefer it, is the bonus.

Print the Fibonacci series

        System.out.print(a + " ");

}

Stream — if they ask for a Java 8 flavour:

Lead withThe iterative loop — O(n) and no stack risk. When they ask for recursion, write it and say “naive recursion is exponential because it recomputes the same values, so I would memoise”. That sentence is the actual answer.
16

Check whether a number is prime

Show solution
public static boolean isPrime(int n) {
    if (n <= 1) return false;          // 0, 1 and negatives are not prime
    if (n <= 3) return true;           // 2 and 3 are
    if (n % 2 == 0) return false;      // no other even number is

    for (int i = 3; i * i <= n; i += 2) {
        if (n % i == 0) return false;
    }
    return true;
}
O(√n) · only odd divisors tested

Follow-up they always ask: "Why stop at the square root?" Because divisors come in pairs: if n = a × b then one of them is at or below √n. Having found none by that point, there are none. Using i * i <= n rather than Math.sqrt(n) also avoids floating-point work in the loop.

Another way to say it

Stream one-liner:

public static boolean isPrime(int n) {
    return n > 1 && IntStream.rangeClosed(2, (int) Math.sqrt(n))
                             .noneMatch(i -> n % i == 0);
}

Sieve of Eratosthenes — if they ask for all primes up to n rather than one check:

boolean[] composite = new boolean[n + 1];

for (int i = 2; (long) i * i <= n; i++) {
    if (!composite[i]) {
        for (int j = i * i; j <= n; j += i) {
            composite[j] = true;
        }
    }
}
Lead withThe loop version with the odd-only optimisation. Then answer the guaranteed follow-up before it lands: “I stop at the square root because divisors come in pairs — if n = a × b, one of them is at or below √n.”

01What's your locator strategy?›

In order of preference: id (unique, fastest), then name, then CSS selector, then relative XPath. Link text and partial link text only for anchors. Never absolute XPath — /html/body/div[3]/div[2]/... breaks the moment anyone adds a wrapper div.

Say this"On projects where I had influence, I asked the dev team to add stable data-test-id attributes. That's the single highest-return thing a lead can negotiate — it kills more flakiness than any framework change."
02XPath vs CSS — when do you need XPath?›

CSS is faster and more readable, and it's what she should reach for by default. XPath is needed when CSS can't do the job:

  • Matching on text — CSS has no text selector. //button[text()='Submit'], //td[contains(text(),'Invoice')]
  • Traversing upward or sideways — CSS only goes down the tree. XPath has .., ancestor::, following-sibling::, preceding-sibling::

The patterns to have ready:

// Partial / dynamic attribute
By.xpath("//input[contains(@id,'userName')]")
By.xpath("//div[starts-with(@class,'toast-')]")

// Label to its input
By.xpath("//label[text()='Email']/following-sibling::input")

// Row cell to the button in the same row
By.xpath("//td[text()='INV-2043']/ancestor::tr//button[@title='Edit']")

// Nth match of a repeated element
By.xpath("(//button[@class='approve'])[2]")

// Two conditions
By.xpath("//input[@type='text' and @name='city']")
03Implicit vs explicit vs fluent wait›
  • Implicit — set once on the driver, applies globally to every findElement/findElements. It waits for presence in the DOM only. Blunt instrument.
  • Explicit — WebDriverWait + an ExpectedCondition, targeted at one element and one condition. Polls every 500ms by default. This is what a framework should use.
  • Fluent — an explicit wait with a configurable polling interval and ignored exception types. Useful for slow, jittery components.
Wait<WebDriver> wait = new FluentWait<>(driver)
        .withTimeout(Duration.ofSeconds(30))
        .pollingEvery(Duration.ofSeconds(2))
        .ignoring(NoSuchElementException.class)
        .ignoring(StaleElementReferenceException.class);
The follow-up that catches people"What happens if you set both implicit and explicit waits?" — They compound unpredictably. Every internal findElement the explicit wait makes while polling inherits the implicit timeout, so a 10-second explicit wait with a 20-second implicit wait can block for far longer than either number. Pick one. In a real framework: implicit wait at zero, explicit waits everywhere.
04Which ExpectedConditions do you use?›
  • presenceOfElementLocated — in the DOM. Not necessarily visible.
  • visibilityOfElementLocated — in the DOM, displayed, and non-zero size
  • elementToBeClickable — visible and enabled. The default for any click
  • invisibilityOfElementLocated — the correct way to wait out a spinner or overlay
  • stalenessOf — waits for an old element to detach; the clean way to wait for a page to actually re-render
  • textToBePresentInElement, attributeToBe, numberOfElementsToBeMoreThan
  • frameToBeAvailableAndSwitchToIt, alertIsPresent, titleContains, urlContains
Follow-up"Difference between presence and visibility?" Presence = the node exists in the DOM. Visibility = it exists and is rendered with height and width. An element hidden by display:none is present but not visible — using presence before a click is a very common source of ElementNotInteractableException.
05StaleElementReferenceException — cause and fix›

A WebElement is a reference to a specific node in the DOM, not a live query. If the page re-renders — an Angular/React re-paint, an AJAX refresh, a navigation — the old node is destroyed and the reference points at nothing. Selenium throws StaleElementReferenceException.

Four fixes, in order of preference:

  • Re-locate the element after the action that triggers the re-render. Don't cache elements across a refresh.
  • In a loop over a table, re-find the list by index each iteration rather than holding a stale List<WebElement>.
  • Wait for ExpectedConditions.stalenessOf(oldElement), then find again — the deterministic version.
  • A retry wrapper that catches the exception and re-attempts once. Last resort, because it can paper over a real timing bug.

09What changed in Selenium 4?›
  • W3C protocol only — the old JSON Wire Protocol is gone, so no more encode/decode translation between the client and the browser driver. Fewer compatibility surprises.
  • DesiredCapabilities is out, Options is in — ChromeOptions, FirefoxOptions.
  • Relative locators — with(By.tagName("input")).toRightOf(label), plus above, below, toLeftOf, near.
  • Timeouts take Duration — Duration.ofSeconds(10), not an int + TimeUnit.
  • New window/tab API — driver.switchTo().newWindow(WindowType.TAB).
  • CDP access — network interception, geolocation, console logs, basic auth, emulating device conditions.
  • Element screenshots — element.getScreenshotAs(OutputType.FILE).
  • Selenium Manager (4.6+) resolves the browser driver automatically, so WebDriverManager is no longer required.
  • Shadow DOM — element.getShadowRoot().
  • Grid rewritten — standalone, hub-node, or fully distributed; Docker-friendly, with observability built in.
10Describe your framework architecture›

The layered answer, top to bottom. She should be able to draw this in 90 seconds.

  • Tests — TestNG classes. Business language only, zero WebDriver calls, zero locators.
  • Page objects — one class per page/component. Private locators, public business methods that return the next page object.
  • Core / utilities — DriverFactory (ThreadLocal), wait helpers, config reader, Excel/JSON data reader, DB utility, API client for test-data setup.
  • Test data — externalised: JSON or Excel for data sets, .properties per environment, never hard-coded in tests.
  • Reporting & listeners — ITestListener that screenshots on failure and attaches it to Extent or Allure; IRetryAnalyzer for a single controlled retry.
  • Build & CI — Maven with surefire, testng.xml suites per scope (smoke / regression), Jenkins pipeline, results published per run.
public class DriverFactory {

12TestNG: annotation order, and the features you actually use›

Execution order: @BeforeSuite → @BeforeTest → @BeforeClass → @BeforeMethod → @Test → @AfterMethod → @AfterClass → @AfterTest → @AfterSuite.

  • priority — lower runs first; all unprioritised tests (default 0) run before higher numbers, alphabetically among themselves.
  • dependsOnMethods — dependent test is skipped, not failed, if the parent fails. Use sparingly; dependencies make suites fragile.
  • groups — smoke, regression, sanity; selected from testng.xml or -Dgroups=.
  • @DataProvider — data-driven runs; can itself be parallel = true.
  • @Parameters + testng.xml — environment and browser injection.
  • invocationCount / threadPoolSize — repeat a test, useful for hunting flakiness.
  • ITestListener — onTestFailure is where the screenshot and the report entry happen.
  • IRetryAnalyzer — one controlled retry.
  • enabled = false to quarantine, @Test(expectedExceptions = ...) for negative tests.
public class RetryAnalyzer implements IRetryAnalyzer {

    private int attempt = 0;
    private static final int MAX_RETRIES = 1;

    @Override
    public boolean retry(ITestResult result) {
        return attempt++ < MAX_RETRIES;
    }
}
Follow-up at lead level"Isn't retrying just hiding flaky tests?" — Yes, if you stop there. The honest answer: retry once so a release isn't blocked by a transient network blip, but log every retry and review the retry rate weekly. A test that retries repeatedly gets quarantined and fixed, not left green.
13Parallel execution — how, and what breaks›

TestNG's parallel attribute in testng.xml: methods, classes, tests, or instances, with thread-count.

<suite name="Regression" parallel="classes" thread-count="4">
    <test name="Chrome">
        <parameter name="browser" value="chrome"/>
        <classes>
            <class name="tests.LoginTests"/>
            <class name="tests.CheckoutTests"/>
        </classes>
    </test>
</suite>

What breaks when you turn it on, in order of frequency:

  • A static or instance WebDriver shared across threads → ThreadLocal
  • Shared ExtentTest object → ThreadLocal too
  • Tests sharing test data — two threads logging in as the same user, or both editing record #1042 → unique data per thread, generated or pooled
  • Order dependence between tests → each test must set up its own state, ideally via API
  • Shared files (a single Excel output, a single screenshot name) → thread-scoped filenames

15Selenium Grid and cross-browser›

Grid distributes tests across machines and browsers. Selenium 4 offers three modes: standalone (everything in one process), hub & node (the classic model), and distributed (router, distributor, session map, event bus — for scale).

Tests connect with RemoteWebDriver pointed at the grid URL, passing browser Options. In CI, the usual setup is Docker containers from selenium/standalone-chrome etc., spun up per pipeline run.

Lead framing"Cross-browser isn't 'run everything everywhere.' I'd run the full regression on the primary browser, and a risk-based subset — auth, payment, critical journeys — on the others. Running 900 tests on four browsers nightly buys very little and costs a lot of maintenance."
16How do you handle a flaky test?›

This is a lead question disguised as a technical one. The structure:

  • Measure first — run it 20 times with invocationCount. Is it flaky, or is it failing for a real reason intermittently?
  • Classify the cause — timing/wait issue, test-data collision, environment instability, test-order dependence, or a genuine product race condition.
  • Fix by cause, not by retry — replace sleeps with explicit conditions, make data unique per run, make the test set up its own state.
  • Quarantine, don't delete — move it out of the blocking suite with a ticket and an owner, so the pipeline stays trustworthy while it's fixed.
  • Track the rate — flaky percentage is a metric she reports, not an anecdote.
Say this"The real cost of a flaky test isn't the rerun — it's that the team stops believing red means broken. Once that happens the whole suite is worthless, so I treat flakiness as a P2 defect in our own code."

01What is REST Assured and how is a test structured?›

A Java DSL for testing REST services — it wraps HTTP calls and JSON/XML parsing so a whole request-and-assert reads as one fluent statement. The structure is BDD:

  • given() — the request: base URI, headers, auth, params, body
  • when() — the HTTP verb and the endpoint
  • then() — the assertions on the response
import static io.restassured.RestAssured.*;
import static org.hamcrest.Matchers.*;

given()
    .baseUri("https://api.company.com")
    .header("Authorization", "Bearer " + token)
    .queryParam("status", "active")
.when()
    .get("/v1/users")
.then()
    .statusCode(200)
    .contentType(ContentType.JSON)
    .body("data.size()", greaterThan(0))
    .body("data[0].email", containsString("@"))
    .body("data.name", hasItem("Aishwarya"))
    .time(lessThan(2000L));
Follow-up"Where do those matchers come from?" Hamcrest — org.hamcrest.Matchers, statically imported. equalTo, hasItem, hasSize, containsString, greaterThan, notNullValue, everyItem.
02POST with a payload, and extracting from the response›

Using a POJO rather than a raw JSON string — this is the answer a lead gives, because POJOs are refactor-safe and reusable.

User payload = new User("Aishwarya", "aishwarya@test.com", "lead");

int newId = given()
        .contentType(ContentType.JSON)   // without this a body POST returns 415
        .body(payload)                   // Jackson/Gson serialises it automatically
    .when()
        .post("/v1/users")
    .then()
        .statusCode(201)
        .body("name", equalTo("Aishwarya"))
        .extract().path("id");

// Deserialise straight back into an object
User created = given().pathParam("id", newId)
    .when().get("/v1/users/{id}")
    .then().statusCode(200)
    .extract().as(User.class);

Assert.assertEquals(created.getEmail(), "aishwarya@test.com");
Follow-up"What if the POJO has fields the API doesn't send?" Configure Jackson to ignore unknown properties (@JsonIgnoreProperties(ignoreUnknown = true)) — otherwise deserialisation throws on any new field the backend adds.
03How do you handle authentication and chain calls?›

Drill 01Java

Comparing values that look identical

This prints one true and one false. Why?

Integer a = 127, b = 127;
Integer c = 128, d = 128;

System.out.println(a == b);
System.out.println(c == d);
Reveal the bug

Bug: comparing wrapper objects with ==, which compares references, not values.

Java caches boxed Integer values from −128 to 127, so a and b are literally the same object and == is true. 128 is outside the cache, so c and d are two separate objects — false.

Fix: c.equals(d), or compare the primitives with c.intValue() == d.intValue().

Drill 02Java

Removing while iterating

This throws at runtime. What and why?

List<String> suites = new ArrayList<>(Arrays.asList("login", "cart", "payment"));

for (String s : suites) {
    if (s.equals("cart")) {
        suites.remove(s);
    }
}
Reveal the bug

Bug: ConcurrentModificationException — structurally modifying a collection while its fail-fast iterator is running.

The enhanced for-loop uses an Iterator that compares modCount on every next(). remove() bumps modCount, the check fails, and it throws.

Fix:

suites.removeIf(s -> s.equals("cart"));

// or, explicitly
Iterator<String> it = suites.iterator();
while (it.hasNext()) {
    if (it.next().equals("cart")) it.remove();
}

On the loop: removeIf is the one to reach for. The iterator version is a while because it runs until the collection is exhausted rather than a fixed number of times — that's what while is for. Anything counted or index-based should be a for.

Nice detail to add: removing the second-to-last element often doesn't throw, because hasNext() returns false before the check runs. That's why it sometimes "works" and makes for a nasty intermittent bug.

Drill 03Java

A verification that never fails

The title on screen is wrong, but this test passes. Why?

String actualTitle = driver.getTitle();

if (actualTitle == "Dashboard") {
    System.out.println("Title verified");
} else {
    System.out.println("Title mismatch");
}
Reveal the bug

Bug: == on Strings compares references.

driver.getTitle() builds a String at runtime, so it is never the same object as the pooled literal "Dashboard" — the comparison is false even when the text matches. And the deeper bug: this is a print statement, not an assertion. The test can never fail either way.

Calling out "there's no assertion here at all" is the answer that impresses a panel — it's the bug behind the bug.

Drill 04Java 8

A stream that blows up on real data

Works in the unit test, throws in the suite. What input breaks it?

Map<String, Integer> lengths = testNames.stream()
        .collect(Collectors.toMap(n -> n, String::length));
Reveal the bug

Bug: duplicate keys throw IllegalStateException: Duplicate key.

Collectors.toMap with two arguments has no rule for what to do when the same key appears twice. The moment the list contains two identical test names, it throws.

Fix: supply a merge function.

Map<String, Integer> lengths = testNames.stream()
        .collect(Collectors.toMap(n -> n, String::length, (existing, replacement) -> existing));

A second gotcha worth mentioning: a null value also throws NullPointerException in toMap, unlike HashMap.put.

Drill 05Selenium

Waits that take far longer than the numbers suggest

The spinner disappears in 2 seconds, but this line sometimes blocks for over a minute. Why?

driver.manage().timeouts().implicitlyWait(Duration.ofSeconds(20));

WebDriverWait wait = new WebDriverWait(driver, Duration.ofSeconds(10));
wait.until(ExpectedConditions.invisibilityOfElementLocated(By.id("spinner")));
Reveal the bug

Bug: mixing implicit and explicit waits.

The explicit wait polls by calling findElement internally. Each of those calls inherits the 20-second implicit wait, so a single poll can block for 20 seconds before the explicit wait even evaluates its condition. The timeouts compound and the behaviour becomes unpredictable — this is documented as unsupported.

Fix: set the implicit wait to zero in the driver factory and use explicit waits exclusively.

driver.manage().timeouts().implicitlyWait(Duration.ZERO);
Drill 06Selenium

The loop that dies on the second row

First iteration passes, second throws. Name the exception and the cause.

List<WebElement> rows = driver.findElements(By.cssSelector("#grid tbody tr"));

for (WebElement row : rows) {
    row.findElement(By.cssSelector(".edit")).click();
    // ... edit the record, save, and come back
    driver.navigate().back();
}
Reveal the bug

Bug: StaleElementReferenceException.

rows holds references to DOM nodes captured before the navigation. navigate().back() reloads the page and destroys every one of them, so the second iteration references nodes that no longer exist.

Fix: re-locate the list on each iteration and index into it.

int count = driver.findElements(By.cssSelector("#grid tbody tr")).size();

for (int i = 0; i < count; i++) {
    WebElement row = driver.findElements(By.cssSelector("#grid tbody tr")).get(i);
    row.findElement(By.cssSelector(".edit")).click();
    // ...
    driver.navigate().back();
    wait.until(ExpectedConditions.visibilityOfElementLocated(By.cssSelector("#grid tbody tr")));
}

Better still: do the edits via API and use the UI only to verify the result — no loop, no staleness.

Drill 07Selenium

Passes alone, fails in parallel

Green when run on its own, random NoSuchWindowException with thread-count="4". Why?

public class BaseTest {

    public static WebDriver driver;

    @BeforeMethod
    public void setUp() {
        driver = new ChromeDriver();
        driver.get(config.getUrl());
    }

    @AfterMethod
    public void tearDown() {
        driver.quit();
    }
}
Reveal the bug

Bug: a static WebDriver shared by every thread.

There is one driver field for the whole JVM. Thread B's setUp() overwrites it while thread A is mid-test, and thread B's quit() kills the session thread A is still using — hence NoSuchWindowException, NoSuchSessionException, and failures that move around between runs.

Fix: one driver per thread via ThreadLocal, with remove() in teardown so pooled threads don't hold a dead session.

private static final ThreadLocal<WebDriver> TL = new ThreadLocal<>();

@BeforeMethod
public void setUp() {
    TL.set(new ChromeDriver());
    TL.get().get(config.getUrl());
}

@AfterMethod
public void tearDown() {
    if (TL.get() != null) {
        TL.get().quit();
        TL.remove();
    }
}
Drill 08Selenium

Chrome processes piling up on the CI agent

After a nightly run the build agent has 200 orphaned chromedriver processes. What's wrong here?

@AfterMethod
public void tearDown() {
    driver.close();
}
Reveal the bug

Bug: close() instead of quit().

close() closes the current browser window only. If the test opened a second tab, the session stays alive; and even with one window, the driver process and session aren't reliably torn down. quit() closes every window and ends the WebDriver session.

Fix: driver.quit() in teardown, guarded with a null check, plus ThreadLocal.remove().

Drill 09Selenium

A negative check that can never pass

This is meant to confirm no error is shown. It always throws. Why?

if (driver.findElement(By.id("errorMsg")) != null) {

Reveal the bug

Bug: findElement never returns null — it throws NoSuchElementException.

So on the happy path, where the error genuinely isn't there, the test explodes instead of passing. The null check is dead code.

Fix: use findElements, which returns an empty list rather than throwing.

Assert.assertTrue(driver.findElements(By.id("errorMsg")).isEmpty(),
        "Error message should not be displayed");

Follow-up to volunteer: for an element that may appear after a delay, assert with invisibilityOfElementLocated instead, so you're not just checking too early.

Drill 10TestNG

A test suite that is always 100% green

Every value below is wrong on screen, and the test still passes. Why?

@Test
public void verifyProfileDetails() {
    SoftAssert soft = new SoftAssert();

    soft.assertEquals(profilePage.name(),  "Aishwarya");
    soft.assertEquals(profilePage.email(), "aishwarya@test.com");
    soft.assertEquals(profilePage.role(),  "Team Lead");
}
Reveal the bug

Bug: missing soft.assertAll().

SoftAssert collects failures instead of throwing. Without the final assertAll() nothing is ever reported and the test always passes — which is worse than having no test at all, because it creates false confidence.

Fix: end with soft.assertAll();. In a framework, enforce it in code review, or extend SoftAssert and call assertAll() from an @AfterMethod.

Drill 11REST Assured

415 Unsupported Media Type

The payload is valid JSON and the endpoint works in Postman. The test gets 415. Why?

given()
    .body(userPayload)
.when()
    .post("/v1/users")
.then()
    .statusCode(201);
Reveal the bug

Bug: no Content-Type on a request that has a body.

The server can't tell how to parse the payload, so it rejects it with 415. Postman sets the header for you when you pick "raw / JSON", which is why it works there and not here — a very common real-world confusion.

Fix:

given()
    .contentType(ContentType.JSON)
    .body(userPayload)
.when()
    .post("/v1/users")
.then()
    .statusCode(201);
Drill 12REST Assured

An assertion that fails on correct data

The response really does contain "id": 101. The assertion fails. Why?

given().spec(reqSpec)
.when().get("/v1/users/101")
.then()
    .statusCode(200)
    .body("id", equalTo("101"));
Reveal the bug

Bug: type mismatch — comparing an Integer to a String.

JsonPath returns 101 as an Integer because the JSON has no quotes around it. equalTo("101") is a String matcher, so it never matches.

Fix: .body("id", equalTo(101)) — or make the coercion explicit with .body("id.toString()", equalTo("101")).

Drill 13Java

NullPointerException on a line with no object on it

The map is definitely not null. So where does the NPE come from?

Map<String, Integer> retryCounts = new HashMap<>();

int count = retryCounts.get("loginTest");
Reveal the bug

Bug: auto-unboxing a null.

get() returns null for a missing key. Assigning it to a primitive int makes the compiler insert .intValue(), and that call is what throws. The NPE is on an invisible method call.

Fix: int count = retryCounts.getOrDefault("loginTest", 0); — or take it as an Integer and null-check.

Say the general rule: any time a wrapper meets a primitive, ask what happens if it's null. It's the single most common NPE in Java code that "looks fine".

Drill 14Java · threading

Dates come out garbled — but only in the nightly run

Works perfectly in local single-threaded runs. In the parallel nightly it produces nonsense dates and the occasional NumberFormatException.

public class DateUtil {

    private static final SimpleDateFormat SDF = new SimpleDateFormat("dd-MM-yyyy");

    public static String today() {
        return SDF.format(new Date());
    }
}
Reveal the bug

Bug: SimpleDateFormat is not thread-safe, and it's being shared as a static field.

It keeps mutable internal state (a Calendar) between calls. Two threads formatting at once corrupt each other's intermediate state — hence dates with digits from two different values, and parse errors that never reproduce locally.

Fix: use java.time, whose formatters are immutable and thread-safe.

private static final DateTimeFormatter FMT = DateTimeFormatter.ofPattern("dd-MM-yyyy");

public static String today() {
    return LocalDate.now().format(FMT);
}
Lead-level add-on"This is the class of bug that makes people distrust the suite — it only appears under parallel load, so it gets written off as flakiness. Whenever I see 'only fails in CI', shared mutable static state is the first thing I look for."
Drill 15Java · Selenium

Intermittent NPE on an attribute check

if (element.getAttribute("value").equals("active")) {
    // ...
}
Reveal the bug

Bug: getAttribute() returns null when the attribute isn't present, and .equals() is then called on null.

Fix — flip the comparison so the literal is the receiver:

if ("active".equals(element.getAttribute("value"))) {
    // ...
}

A String literal is never null, so this can't throw. Objects.equals(a, b) does the same job and reads better when neither side is a literal.

Drill 16Java

A test that reports success on a broken application

@Test
public void verifyCheckout() {
    try {
        cartPage.proceedToPayment();
        Assert.assertTrue(paymentPage.isLoaded(), "Payment page did not load");
    } catch (Exception e) {
        e.printStackTrace();
    }
}
Reveal the bug

Bug: the catch block swallows every failure.

Any WebDriverException — element missing, page never loaded, session died — gets printed to the console and the method returns normally. TestNG sees no exception, so the test is green on a completely broken checkout.

Fix: delete the try/catch entirely. Let the exception propagate; that's how the test reports failure.

If context genuinely needs adding, catch, enrich, and rethrow:

catch (WebDriverException e) {
    throw new AssertionError("Checkout failed for cart " + cartId, e);
}

Note the subtlety: Assert throws AssertionError, which extends Error, not Exception — so this particular catch wouldn't swallow the assertion, only the Selenium failures before it. Spotting that detail is a strong answer.

Drill 17Java

The pass rate always prints as 0.0%

int passed = 7;
int total  = 9;

double passRate = passed / total * 100;

System.out.println("Pass rate: " + passRate + "%");
Reveal the bug

Bug: integer division happens before the assignment to double.

7 / 9 is evaluated as ints and truncates to 0, then 0 * 100 is 0. The result is widened to a double only afterwards, by which point the precision is long gone.

Fix: force one operand to double before the divide.

double passRate = (double) passed / total * 100;   // 77.77...
Drill 18Java 8

IllegalStateException on the second line that uses the stream

Stream<WebElement> rows = driver.findElements(By.cssSelector("#grid tbody tr")).stream();

long rowCount = rows.count();

List<String> firstColumn = rows
        .map(r -> r.findElement(By.tagName("td")).getText())
        .collect(Collectors.toList());
Reveal the bug

Bug: "stream has already been operated upon or closed" — a Stream can only be consumed once.

count() is a terminal operation, so the stream is spent. Any further use throws IllegalStateException.

Fix: collect to a List once, then work from that.

List<WebElement> rows = driver.findElements(By.cssSelector("#grid tbody tr"));

int rowCount = rows.size();

List<String> firstColumn = rows.stream()
        .map(r -> r.findElement(By.tagName("td")).getText())
        .collect(Collectors.toList());

The bonus point: a List is reusable, a Stream isn't. That distinction is the whole answer.

Drill 19TestNG

Tests pass individually, fail when the class runs as a whole

public class AccountTests extends BaseTest {

    @BeforeClass
    public void setUp() {
        driver = new ChromeDriver();
        loginPage.loginAs("admin", "admin123");
    }

    @Test
    public void testChangePassword() { /* logs out at the end */ }

    @Test
    public void testUpdateProfile() { /* assumes still logged in */ }
}
Reveal the bug

Bug: tests share state and depend on execution order.

@BeforeClass runs once for the whole class, so both tests share one browser and one session. testChangePassword logs out, and whichever test runs after it inherits a logged-out browser. TestNG gives no ordering guarantee between unprioritised tests, so which one breaks changes between runs.

Fix: make every test independent — @BeforeMethod for a fresh session and a known starting state.

Say this"My rule is that any test must be able to run on its own, first, or in any order. The moment tests depend on each other you can't run them in parallel, you can't rerun a single failure, and the suite gets slower and less trustworthy at the same time."
Drill 20TestNG

"Data provider mismatch" before any test runs

@DataProvider(name = "credentials")
public Object[][] credentials() {
    return new Object[][] {
            { "admin", "admin123" },
            { "guest", "guest123" }
    };
}

@Test(dataProvider = "credentials")
public void login(String username) {
    loginPage.loginAs(username, "default");
}
Reveal the bug

Bug: the data provider supplies two values per row; the test method accepts one.

TestNG maps each element of the inner array onto a parameter positionally, so the arity must match exactly. It fails at configuration time with "Data provider mismatch", which is why nothing runs at all.

Fix: public void login(String username, String password).

Follow-up worth volunteering: a data provider can also take a Method parameter, so one provider can return different data depending on which test is asking for it.

Drill 21TestNG

One failure, and suddenly forty tests are "skipped"

@AfterMethod
public void verifyNoConsoleErrors() {
    Assert.assertTrue(
            driver.findElements(By.cssSelector(".js-error")).isEmpty(),
            "JS errors present on page");
}
Reveal the bug

Bug: asserting inside a configuration method.

A failure in @AfterMethod is a configuration failure, not a test failure. TestNG reports it separately, the test that actually ran is misattributed, and depending on the suite setup it can cascade into everything after it being skipped rather than executed.

Fix: configuration methods do setup and cleanup only. Verification belongs in the test, or in a listener that records the problem without failing the configuration.

Same family of bug: putting driver.quit() behind an assertion — when the assert fails, the browser never closes and the CI agent leaks sessions.

Drill 22TestNG XML

Parallel is configured, and the suite still takes 90 minutes

<suite name="Regression" parallel="tests" thread-count="8">

    <test name="Full regression">
        <classes>
            <class name="tests.LoginTests"/>
            <class name="tests.CartTests"/>
            <class name="tests.CheckoutTests"/>

Bug: parallel="tests" parallelises <test> tags — and there is only one.

Drill 23Maven

"No tests to run" — but the tests are right there

mvn test finishes in four seconds and reports zero tests. The class is src/test/java/tests/LoginValidation.java and it definitely has @Test methods.

Reveal the bug

Bug: the class name doesn't match Surefire's default include patterns.

Maven Surefire only picks up Test*.java, *Test.java, *Tests.java and *TestCase.java. LoginValidation matches none of them, so it's never discovered.

Fix — rename it to LoginValidationTest, or point Surefire at the suite file explicitly:

<plugin>
    <artifactId>maven-surefire-plugin</artifactId>
    <version>3.2.5</version>
    <configuration>
        <suiteXmlFiles>
            <suiteXmlFile>testng.xml</suiteXmlFile>
        </suiteXmlFiles>
    </configuration>
</plugin>

Related question they may add: surefire runs unit tests in the test phase; failsafe runs integration tests in verify, and unlike surefire it doesn't fail the build immediately — so post-integration cleanup still gets to run.

Drill 24Maven

Compiles in the IDE, fails on the build server

BaseTest.java lives in src/main/java and imports org.testng.annotations.Test. Locally it's fine; CI fails with "package org.testng does not exist".

Reveal the bug

Bug: a test-scoped dependency used from main source.

<dependency>
    <groupId>org.testng</groupId>
    <artifactId>testng</artifactId>
    <version>7.9.0</version>
    <scope>test</scope>
</dependency>

scope=test puts the jar on the test classpath only. src/main/java compiles against the compile classpath, where TestNG isn't present. The IDE often papers over this by using one merged classpath, which is why it only breaks in CI.

Fix: move framework and test classes into src/test/java where they belong. Don't widen the scope to compile to make the error go away — that ships TestNG into the production artifact.

Know the scopes: compile (default, everywhere), test, provided (at compile time, supplied at runtime by the container), runtime (not needed to compile).

Drill 25Selenium

clear() appears to work, then the old value comes back

On a React form: the field visibly empties, the new value types in, and on submit the original value is saved.

quantityField.clear();
quantityField.sendKeys("5");
Reveal the bug

Bug: clear() empties the DOM value without firing the input events the framework listens for.

React, Angular and Vue keep their own model and update the DOM from it. clear() changes the DOM directly, the framework's state never hears about it, and on the next re-render the model overwrites the field.

Fix — clear the way a user would, with keystrokes:

quantityField.sendKeys(Keys.chord(Keys.CONTROL, "a"), Keys.DELETE);
quantityField.sendKeys("5");

Then assert the field actually holds what you typed: assertEquals(quantityField.getAttribute("value"), "5"). Trust nothing on a reactive form.

Drill 26Selenium

getText() returns an empty string on an element that's clearly there

String total = driver.findElement(By.id("orderTotal")).getText();

Assert.assertEquals(total, "1500");   // expected [1500] but found []
Reveal the bug

Bug: getText() returns only rendered text, so a present-but-not-visible element yields an empty string.

The element is in the DOM — hence no NoSuchElementException — but it's inside a collapsed panel, scrolled out of the rendering path, or still display:none while the page settles.

Fix — wait for visibility, which is what the assertion actually depends on:

WebElement total = wait.until(
        ExpectedConditions.visibilityOfElementLocated(By.id("orderTotal")));

Assert.assertEquals(total.getText(), "1500");

The escape hatch, and its caveat: getAttribute("textContent") returns the text regardless of visibility — useful for genuinely hidden content, but if the user can't see it, ask whether the assertion is testing the right thing at all.

Drill 27Design smell

Nothing throws. What's wrong with this page object?

The final drill, and the one most likely to be asked at lead level — the code works perfectly.

public class LoginPage {

    WebDriver driver;

    public WebElement getUsernameField() {
        return driver.findElement(By.id("userName"));
    }

    public WebElement getPasswordField() {
        return driver.findElement(By.id("password"));
    }

    public WebElement getSignInButton() {
        return driver.findElement(By.cssSelector("button[type='submit']"));
    }
}

// in the test
loginPage.getUsernameField().sendKeys("admin");
loginPage.getPasswordField().sendKeys("admin123");
loginPage.getSignInButton().click();
Reveal the bug

Bug: it isn't a page object — it's a locator dictionary. The Page Object pattern is being violated while appearing to be followed.

  • The abstraction leaks. Returning WebElement puts the Selenium API back in the test. The test now knows about sendKeys and click, which is exactly what POM exists to prevent.
  • No reuse. Those three lines get copy-pasted into every test that needs a login, instead of one loginAs(user, pass).
  • Nowhere to put the waiting. With no behaviour in the page class, every test has to do its own synchronisation.
  • No navigation model. A proper action method returns the next page object, so the test reads as a journey.
  • Package-private driver field — should be private (or protected on a BasePage), and final.

Fix:

public class LoginPage extends BasePage {

    private final By username = By.id("userName");
    private final By password = By.id("password");
    private final By signIn   = By.cssSelector("button[type='submit']");

    public LoginPage(WebDriver driver) { super(driver); }

    public DashboardPage loginAs(String user, String pass) {
        type(username, user);
        type(password, pass);
        click(signIn);
        return new DashboardPage(driver);
    }
}
Say this"The test should read like a user story. If I can see By.id or sendKeys in a test class, the page object isn't doing its job — and I'll find out the hard way the next time the login page is redesigned and I have to change forty files instead of one."

Method

How to answer a "find the bug" question out loud

Panels score the reasoning, not just the answer. This four-beat structure works even when she isn't immediately sure.

1 · Narrate what the code is trying to do

"This is looping over grid rows and clicking edit on each." Buys thinking time and shows comprehension even before the defect is found.

2 · Name the defect and its exception

"It'll throw StaleElementReferenceException on the second iteration." Specific beats vague — name the exact exception class.

3 · Explain the mechanism

"Because navigate().back() reloads the DOM and the cached references detach." This is the part that separates memorised from understood.

4 · Give the fix, then the better fix

"Re-find by index each iteration — though honestly I'd set the data up via API and skip the loop." That second sentence is the lead-level answer.

The round that decides the title

Lead round

Two engineers can both write a wait utility. Only one of them can decide what gets automated, defend an estimate, and tell a PM the release isn't ready. That's what's being tested here.

The 90-second framework pitch

The single highest-value thing to rehearse. Timed, out loud, three times. Structure it like this, and stop at 90 seconds — let them ask for detail.

Context (15s) — "It was a hybrid framework for a [domain] web app: Java, Selenium 4, TestNG, Maven, running on Jenkins. About [N] tests, [N] minutes for the regression."

Structure (30s) — "Four layers: tests, page objects, a core utility layer, and reporting. Tests contain no locators and no WebDriver calls. Driver lifecycle is in a factory using ThreadLocal so we can run parallel. Waits all go through one utility — implicit wait is set to zero deliberately."

Data & config (15s) — "Test data is external — JSON plus a properties file per environment. Setup happens over API wherever possible rather than through the UI."

Execution (15s) — "TestNG suites split by scope: smoke on every PR, full regression nightly. Listener screenshots on failure into Allure, one retry with the retry rate tracked."

The decision you owned (15s) — "The change I'm proudest of: we moved data setup from UI to API and cut regression runtime from [X] to [Y] and the flaky rate from [X]% to [Y]%." Have real numbers here, even approximate ones.

Do notStart with the folder structure. Every candidate does this and it signals "I built it from a tutorial." Start with the problem the framework solved.
01How do you decide what to automate?›

Risk and repetition, not coverage percentage.

  • Automate: critical business journeys, regression-prone areas, anything run every release, data-heavy validations, and anything on the revenue path
  • Don't automate: one-off exploratory checks, screens changing every sprint, tests where the setup cost exceeds the manual run cost, and anything genuinely needing human judgement (visual polish, usability)
  • Push down the pyramid: if it can be tested at API or unit level, it shouldn't be a UI test
Say this"I don't chase 100% automation. I chase 100% of the critical path automated and running on every build, and I'd rather have 200 tests the team trusts than 900 they ignore."
02How do you estimate automation effort?›
  • Classify scenarios as simple / medium / complex, attach an hours figure to each from historical data (e.g. 2 / 4 / 8 hours), and multiply
  • Add framework and environment setup as a separate one-off line — this is where estimates usually break
  • Add a maintenance allowance, typically 15–20% of build effort per cycle
  • Add a buffer for unstable environments and unavailable test data, and name it explicitly rather than hiding it
  • Give a range with assumptions, not a single number: "12–15 days, assuming the QA environment is stable and test accounts are provisioned by day 2"
03Which metrics do you report?›
MetricWhy it matters
Automation coverage of critical pathBetter than raw "% automated"
Pass rate per run & trendA falling trend is an early warning
Flaky rateThe trust metric. Track it or the suite rots
Execution timeFeedback speed is what makes CI useful

04What do you look for in an automation code review?›
  • Can this test fail? Missing assertAll(), print instead of assert, try/catch swallowing the failure
  • Any Thread.sleep()? Automatic change request
  • Locators in the test class instead of the page object
  • Hard-coded data — URLs, credentials, record IDs, dates
  • Test independence — does it assume another test ran first?
  • Cleanup — does it leave data behind that will break the next run?
  • Assertion messages — a failure should be diagnosable from the report alone, without re-running locally
  • Naming — the test name should say what behaviour is being verified
05Your regression is red on release day. What do you do?›

They want to see triage under pressure, and whether she'll hold the line.

  • Triage by cause first — separate genuine product defects from environment issues, test-data problems and test bugs. Usually 10 minutes of work that changes the entire conversation
  • Assess by severity and area — three failures in payment is a different conversation from thirty in a deprecated report screen
  • Give the stakeholders a risk statement, not a verdict — "these two are real defects on the checkout path, this is the user impact, this is what it takes to fix"
  • Be clear about the recommendation and who owns the decision — she recommends; the business decides go/no-go; and she documents the accepted risk either way
Say this"I'll never say 'don't ship.' I'll say 'here's what's broken, here's who it affects, here's the workaround, and here's my recommendation' — and then support whatever call the business makes, with the risk written down."
06How do you handle a developer who says your defect is invalid?›

Structure: evidence, not opinion; requirement, not preference; escalate the question, never the person.

  • Reproduce it cleanly, with steps, environment, build number, logs, screenshot or video
  • Anchor it to the acceptance criteria or the requirement — "this is what the story says" is a much shorter conversation than "this feels wrong"
  • If it's genuinely ambiguous, take it to the BA or PO as a clarification, not a dispute
  • If it's a real disagreement on severity, let the product owner decide priority — that's their call, not either of yours
07How do you bring the team along — mentoring, onboarding, ownership?›
  • Onboarding — a running framework on day one, a small real test as the first task, paired review on the first PR
  • Distribute ownership — each engineer owns a module's tests end to end, so nobody is just executing someone else's plan
  • Review as teaching — comments explain the why, and the same recurring comment becomes a documented standard instead of being repeated
  • Regular knowledge sharing — a short weekly session where someone demos something they built
  • Protect focus — shielding the team from churn is a real part of the job
08Where does automation sit in the sprint? (shift-left / in-sprint)›
  • QA in refinement, challenging acceptance criteria before code is written — the cheapest defect is the one caught in a conversation
  • Test cases written alongside development, not after
  • API tests written against the contract while the UI is still being built
  • Automation is part of the story's definition of done, not a follow-up ticket that never gets picked up
  • Smoke on every PR, full regression nightly, results visible to the whole team
Honest framing beats a perfect answerIf her last project didn't work this way, say so and say what she'd change: "We automated a sprint behind, and the backlog grew. If I were setting it up now I'd make automation part of DoD from sprint one." Panels trust that far more than a textbook description.
09Your four STAR stories — fill these in before the interview›

Situation, Task, Action, Result — with a number in the Result every time. Prepare exactly these four; almost every behavioural question maps onto one of them.

A · Something you built or rebuilt

Framework from scratch, or a migration (Selenium 3→4, adding parallel, adding API layer). Result = runtime, coverage or flakiness numbers.

B · A crisis you handled

Production defect, broken release, suite red on go-live day. Result = how it was contained and what changed afterwards so it couldn't recur.

C · A person you developed

D · A disagreement you navigated

With a dev lead, a PM, or a client. Result = the decision reached and the relationship intact. Never make the other person the villain.

11What to do when she genuinely doesn't know›

This will happen, and it isn't fatal. Bluffing is. The formula:

Mechanism

One test, end to end

If she can narrate this sequence, she understands the framework rather than having memorised its parts. Worth rehearsing out loud.

  1. Maven starts Surefire, which is pointed at testng.xml rather than scanning for *Test classes.
  2. TestNG reads the suite, sees parallel="classes", and hands each test class to a different thread.
  3. @BeforeMethod in BaseTest fires on that thread and calls DriverFactory.init().
  4. The factory builds a browser for the requested type, sets the implicit wait to Duration.ZERO, and stores the driver in this thread's ThreadLocal slot.
  5. The test runs. It asks LoginPage to loginAs(...) — it never touches WebDriver.
  6. The page object calls type() and click() on BasePage, which route through Waits.
  7. Waits builds a WebDriverWait for this thread's driver and blocks on an explicit condition — elementToBeClickable, not a sleep.
  8. The action method returns the next page object, so the test continues in business language.
  9. The test asserts and either passes, or throws.
  10. On failure, TestListener.onTestFailure fires, grabs a screenshot from this thread's driver and writes it to target/screenshots.
  11. @AfterMethod calls DriverFactory.quit() — quit() to end the session, then remove() so the pooled thread doesn't carry a dead reference into the next test.
Say this

"Steps 4 and 11 are the ones that matter. Everything else is conventional — the thread-scoped driver and the matching cleanup are what make the suite safe to run in parallel."

1 · The test — business language, nothing else

src/test/java/tests/ui/LoginTest.java 
@Test(groups = "smoke", description = "Valid credentials land on the products page")
public void validLoginLandsOnProducts() {
    ProductsPage products = new LoginPage(DriverFactory.get())
            .loginAs(Config.get("ui.username"), Config.get("ui.password"));

Say this

"Read that out and it's a sentence: log in as the standard user, land on products. No By, no sendKeys, no URL, no password. If a locator changes, this file never moves."

2 · The page object — the abstraction boundary

src/test/java/pages/LoginPage.java 
public class LoginPage extends BasePage {

    private final By username = By.id("user-name");
    private final By password = By.id("password");
    private final By loginBtn = By.id("login-button");
    private final By error    = By.cssSelector("[data-test='error']");

    public LoginPage(WebDriver driver) {
        super(driver);
    }

    /** Returns the page the user lands on, so tests read like a journey. */
    public ProductsPage loginAs(String user, String pass) {
        type(username, user);
        type(password, pass);
        click(loginBtn);
        return new ProductsPage(driver);
    }

    public String errorMessage() {
        return textOf(error);
    }
}

Three things to point at: locators are private final, no method returns a WebElement, and loginAs returns the next page object.

What breaks without it

Make those methods return WebElement and it becomes a locator dictionary — the Selenium API leaks back into every test, there's nowhere to put the waiting, and the same three lines get copy-pasted into forty files. That's Spot-the-Bug drill 27, and it's the lead-level version of this question because the code still works.

3 · BasePage — shared behaviour, protected not public

src/test/java/pages/BasePage.java 
public abstract class BasePage {

    protected final WebDriver driver;

    protected BasePage(WebDriver driver) {
        this.driver = driver;
    }

    protected void click(By locator) {
        Waits.clickable(locator).click();
    }

    protected void type(By locator, String text) {
        WebElement field = Waits.visible(locator);
        field.clear();
        field.sendKeys(text);
    }

    protected String textOf(By locator) {
        // getText() returns only RENDERED text, so waiting for visibility
        // (not just presence) is part of the assertion being correct.
        return Waits.visible(locator).getText().trim();
    }
}
Say this

"Abstract class rather than an interface, because it holds state — the driver — and has a constructor. A page genuinely is a kind of page. Interfaces are for 'is able to', which is why the listener and the retry analyzer are interfaces."

And note protected, not public: every page can use these helpers, no test can.

4 · Waits — one door, so nobody can reintroduce a sleep

src/test/java/core/Waits.java 
private static WebDriverWait newWait() {
    return new WebDriverWait(
            DriverFactory.get(),
            Duration.ofSeconds(Config.getInt("wait.timeout")));
}

/** Visible AND enabled - the correct condition before any click. */
public static WebElement clickable(By locator) {
    return newWait().until(ExpectedConditions.elementToBeClickable(locator));
}

/** In the DOM - but NOT necessarily visible. Rarely what you want before a click. */
public static WebElement present(By locator) {
    return newWait().until(ExpectedConditions.presenceOfElementLocated(locator));
}
Say this

"Every wait in the framework goes through this one class. One place to change the timeout, one place to add logging, and no way for someone to quietly add a Thread.sleep in a pull request without it being obvious."

A detail worth volunteering

The method is called newWait(), not wait() — a static wait() won't compile, because it clashes with Object.wait(). Mentioning that shows she's actually written this code rather than recited it.

5 · DriverFactory — the class to know cold

src/test/java/core/DriverFactory.java 
public final class DriverFactory {

    private static final ThreadLocal<WebDriver> DRIVER = new ThreadLocal<>();

    public static void init() {
        String browser   = System.getProperty("browser", "chrome");
        boolean headless = Boolean.parseBoolean(System.getProperty("headless", "false"));

        WebDriver driver;
        // ... build ChromeDriver / FirefoxDriver / EdgeDriver from Options ...

        // Deliberately ZERO. All waiting goes through Waits, using explicit conditions.
        driver.manage().timeouts().implicitlyWait(Duration.ZERO);

        DRIVER.set(driver);
    }

    public static WebDriver get() {
        WebDriver driver = DRIVER.get();
        if (driver == null) {
            throw new IllegalStateException(
                    "No driver for this thread. Did the test class extend BaseTest?");
        }
        return driver;
    }

    public static void quit() {
        WebDriver driver = DRIVER.get();
        if (driver != null) {
            driver.quit();   // quit(), not close() - ends the session, not just a window
            DRIVER.remove(); // critical: pooled threads are reused
        }
    }
}

Four deliberate decisions in one small class: ThreadLocal not static, implicit wait at zero, quit() not close(), and remove() in teardown. Each one is its own interview question.

6 · The listener — cross-cutting, so it isn't in the tests

src/test/java/listeners/TestListener.java 
@Override
public void onTestFailure(ITestResult result) {
    String name = result.getMethod().getMethodName();

    if (!DriverFactory.isStarted()) {
        System.out.println("[FAILED] " + name + " (no browser - API test)");
        return;
    }

    try {
        Files.createDirectories(SHOTS);
        byte[] png = ((TakesScreenshot) DriverFactory.get())
                .getScreenshotAs(OutputType.BYTES);

        Path target = SHOTS.resolve(name + "_" + LocalDateTime.now().format(STAMP) + ".png");
        Files.write(target, png);

    } catch (Exception e) {
        // Never let the listener mask the real test failure.
        System.out.println("Could not capture screenshot: " + e.getMessage());
    }
}
Say this

"Screenshot-on-failure is written once, here, instead of a try/catch in every test. The guard matters too — the same listener runs for API tests where there's no browser, and the catch means a failure in the listener can never hide the failure in the test."

Note STAMP is a DateTimeFormatter, not a SimpleDateFormat. It's a shared static field and SimpleDateFormat isn't thread-safe — in a parallel run it would produce garbled filenames that never reproduce locally.

The follow-ups

Five decisions, and what breaks without them

The panel will pick one of these and dig. Each has an exercise in the project — do the exercise, see the failure, and the answer stops being theoretical.

1 · ThreadLocal, not a static WebDriver

Exercise 1 in the README

Change DriverFactory to private static WebDriver driver and run run.cmd ui. The suite falls over with NoSuchWindowException. Put it back. Having seen it is worth more than knowing it.

2 · Implicit wait set to zero

It's one line, and it's deliberate: driver.manage().timeouts().implicitlyWait(Duration.ZERO).

What breaks without it

Mixing an implicit wait with explicit waits makes the timeouts compound. The explicit wait calls findElement internally while polling, and each of those inherits the implicit timeout — so a 10-second explicit wait under a 20-second implicit wait can block far longer than either number. Setting it to zero in one place means nobody can reintroduce the mix later.

3 · @BeforeMethod, not @BeforeClass

A fresh browser per test costs a few seconds and buys test independence.

Say this

"Any test has to be able to run alone, first, or in any order. The moment tests depend on each other you can't parallelise, you can't rerun a single failure, and the suite gets slower and less trustworthy at the same time."

4 · Surefire pointed at the suite file

Without suiteXmlFiles, Surefire only discovers classes matching Test*, *Test, *Tests or *TestCase. Pointing it at testng.xml puts TestNG in charge of what runs, which is how run.cmd api and run.cmd ui select different subsets.

A real one from building this

The pom pins Surefire to 3.5.0 with a comment. On 3.6.0 the suiteXmlFiles setting was ignored and it silently fell back to scanning for *Test classes — so the API-only run quietly executed the whole suite. "I pinned it and left a comment saying why" is a good thing to be able to say about your own build file.

5 · Retry once, but log every retry

src/test/java/listeners/RetryAnalyzer.java 
@Override
public boolean retry(ITestResult result) {
    if (attempt < MAX_RETRIES) {
        attempt++;
        System.out.println("[RETRY " + attempt + "/" + MAX_RETRIES + "] "
                + result.getMethod().getMethodName()
                + " - first failure: " + result.getThrowable());
        return true;
    }
    return false;
}
When they push back with "isn't that hiding flaky tests?"

"Yes, if you stop there. It retries once so a transient blip doesn't block a release — but it prints every retry, and I review the retry rate weekly. A test that keeps retrying gets quarantined and fixed, not left green. The real cost of flakiness isn't the rerun, it's that the team stops believing red means broken."

The API layer

Same framework, no browser. This is the part that lets her talk about the test pyramid with something concrete behind it.

src/test/java/tests/api/BookingApiTest.java 
@BeforeClass(alwaysRun = true)
public void setUpSpecs() {
    String baseUri = Config.get("api.baseUri");

    token = given()
                .baseUri(baseUri)
                .relaxedHTTPSValidation()
                .contentType(ContentType.JSON)
                .body(Map.of("username", Config.get("api.username"),
                             "password", Config.get("api.password")))
            .when()
                .post("/auth")
            .then()
                .statusCode(200)
                .extract().path("token");

    requestSpec = new RequestSpecBuilder()
            .setBaseUri(baseUri)
            .setRelaxedHTTPSValidation()
            .setContentType(ContentType.JSON)
            .addHeader("Accept", "application/json")
            .addFilter(new RequestLoggingFilter())
            .build();

    resSpec = new ResponseSpecBuilder()
            .expectStatusCode(200)
            .expectContentType(ContentType.JSON)
            .expectResponseTime(lessThan(10_000L))
            .build();
}

Then every test is three lines of intent:

Integer id = given()
        .spec(requestSpec)
        .body(payload)                       // Jackson serialises the POJO
    .when()
        .post("/booking")
    .then()
        .statusCode(200)
        .body("booking.firstname", equalTo("Aishwarya"))
        .body("booking.totalprice", equalTo(850))   // Integer, NOT "850"
        .extract().path("bookingid");
Say this

"Auth happens once per class, not once per test. A suite that logs in before every test hammers the auth service and starts getting rate-limited — and those failures look exactly like flakiness, but they're self-inflicted."

Two real bugs found while building this — both good stories

415 → then 418. The POST first failed with 415 Unsupported Media Type because the body had no Content-Type. Fixed that, then got 418 — because setAccept(ContentType.JSON) sends a multi-value Accept header that this API rejects on writes. Pinning a literal application/json fixed it.

The lesson is the transferable bit: when an API works in Postman but not in REST Assured, compare the actual headers. log().all() shows exactly what was sent.

Anticipate

What they'll ask about it

"How many tests, and how long does the regression take?"›

Have real numbers ready from her actual last project — test count, runtime before and after parallel, flaky rate. Approximate is fine; vague is not. "Around 400 tests, regression was about 3 hours before we parallelised, roughly 50 minutes after" is a complete answer. "Quite a lot" is not.

"What would you change if you started again?"›

A lead must have an answer here; "nothing" reads as inexperience. Good options: move more setup to API earlier, add contract/schema tests sooner, build the reporting in from day one rather than bolting it on, or negotiate data-test-id attributes with the dev team at the start.

"Why TestNG and not JUnit 5?"›

Honest answer: for UI suites TestNG's built-in suite XML, groups, data providers, parallel configuration and IRetryAnalyzer cover the needs without extra libraries. JUnit 5 is excellent and has parallel execution too, but the suite-level orchestration takes more assembly. Then add: "It's not a religious position — I'd use whatever the team already runs."

"How do you handle test data?"›

Externalised — a properties file per environment, JSON or Excel for data sets, and data providers for parameterised runs. For anything stateful, create it via API at the start of the test and clean it up afterwards, so tests never share a record. Point at Config.java: no test class contains a URL or a password.

"Where does this run in CI?"›

Smoke group on every pull request, full regression nightly, both in Jenkins. Headless in CI via -Dheadless=true, browser selectable via -Dbrowser=. Results published per run; screenshots attached to failures. For scale, the same tests point at a Grid or Dockerised browsers by swapping the driver construction in the factory — which is the reason driver creation is isolated in one class.

"Show me how you'd add a new page."›

This is the best possible question, because the answer is a two-minute live demo: create a class extending BasePage, add private final By locators, add one business method that returns the next page object, write the test. Exercise 5 in the project README is exactly this — CartPage. Doing it once beforehand makes the answer fluent.

  • implicit 20 + explicit 10 → timeouts compound
  • static WebDriver → threads overwrite each other
  • close() in teardown → leaks driver processes
  • findElement(...) != null → it throws, never returns null
  • remove inside for-each → ConcurrentModificationException
