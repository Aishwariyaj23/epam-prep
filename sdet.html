01GPath — the thing most REST Assured users never learn›

The string inside body("...") isn't JsonPath — it's Groovy GPath. That means you can run closures inside the assertion, and filter, project and aggregate without pulling the response into Java first.

// every user over 30, by name
.body("users.findAll { it.age > 30 }.name", hasItems("Meera", "Karthik"))

// the one matching a condition, then a field off it
.body("users.find { it.email == 'a@test.com' }.id", equalTo(101))

// projection
.body("orders.items.flatten().sku", everyItem(notNullValue()))

// aggregates - computed server-side data, checked in one line
.body("orders.total.sum()", equalTo(4820))
.body("orders.total.max()", lessThan(5000))
.body("users.age.min()", greaterThanOrEqualTo(18))

// count with a condition
.body("users.findAll { it.active == true }.size()", equalTo(7))

// sorting check, entirely in the assertion
.body("products.price", equalTo(new ArrayList<>(response.path("products.price"))))
Why it lands

"I use GPath closures so filtering happens in the assertion rather than in Java. It keeps the test declarative, and the failure message shows the actual collection rather than a boolean." Almost nobody says this.

The gotcha

GPath's syntax is Groovy, not Java — it is the implicit variable, == compares by value, and single quotes are strings. And .find returns the first match while .findAll returns a list; mixing them up gives confusing type errors in the matcher.

02Deserialising generics — why as(List.class) isn't enough›

Java erases generic types at runtime, so .as(List.class) gives you a List<LinkedHashMap>, not a List<User>. You find out via a ClassCastException somewhere far from the cause.

// wrong - compiles, then explodes later
List<User> users = response.as(List.class);

// right - TypeRef carries the generic type through
List<User> users = response.as(new TypeRef<List<User>>() {});

// or via jsonPath with a target type
List<User> users = response.jsonPath().getList("data", User.class);

// single object
User user = response.as(User.class);

Configure the mapper once, globally, rather than per call:

RestAssured.config = RestAssuredConfig.config()
    .objectMapperConfig(new ObjectMapperConfig()
        .jackson2ObjectMapperFactory((type, charset) -> {
            ObjectMapper mapper = new ObjectMapper();
            mapper.configure(DeserializationFeature.FAIL_ON_UNKNOWN_PROPERTIES, false);
            mapper.setSerializationInclusion(JsonInclude.Include.NON_NULL);
            mapper.registerModule(new JavaTimeModule());
            return mapper;
        }));
Follow-up

"What happens when the API adds a field?" Without FAIL_ON_UNKNOWN_PROPERTIES=false (or @JsonIgnoreProperties), every test deserialising that payload breaks on a backwards-compatible change. And NON_NULL on serialisation matters too — otherwise your POJO sends explicit nulls that a PATCH endpoint may treat as "clear this field".

03Filters — cross-cutting behaviour without touching every test›

A Filter wraps every request/response pair. It's where correlation IDs, timing, report attachments and conditional logging belong.

public class CorrelationIdFilter implements Filter {

    @Override
    public Response filter(FilterableRequestSpecification req,
                           FilterableResponseSpecification res,
                           FilterContext ctx) {

        String correlationId = UUID.randomUUID().toString();
        req.header("X-Correlation-Id", correlationId);

        long start = System.currentTimeMillis();
        Response response = ctx.next(req, res);   // the call itself
        long elapsed = System.currentTimeMillis() - start;

        if (response.statusCode() >= 400) {
            System.out.printf("FAILED %s %s -> %d in %dms (correlation %s)%n",
                    req.getMethod(), req.getURI(), response.statusCode(), elapsed, correlationId);
        }
        return response;
    }
}
The senior point

"I put a correlation ID on every request from a filter. When an API test fails in CI, I can hand that ID to the backend team and they find the exact request in their logs. It turns 'the test failed' into 'here is your trace'."

Built-ins worth naming: RequestLoggingFilter, ResponseLoggingFilter, ErrorLoggingFilter, and Allure's AllureRestAssured.

04WireMock — testing what you can't reach›

A stub server standing in for a dependency you don't control. It answers three questions a real environment can't: what if the dependency is slow, broken, or returns something weird?

WireMockServer wm = new WireMockServer(options().port(8089));
wm.start();

// a normal stub
wm.stubFor(get(urlPathEqualTo("/payments/status"))
        .withQueryParam("id", equalTo("P-1001"))
        .willReturn(okJson("{\"status\":\"SETTLED\"}")));

// fault injection - the tests you cannot write against a real service
wm.stubFor(get(urlPathEqualTo("/payments/slow"))
        .willReturn(aResponse().withFixedDelay(5000)));

wm.stubFor(get(urlPathEqualTo("/payments/broken"))
        .willReturn(aResponse().withFault(Fault.CONNECTION_RESET_BY_PEER)));

// stateful: first call PENDING, second call SETTLED
wm.stubFor(get("/payments/1").inScenario("settle")
        .whenScenarioStateIs(STARTED)
        .willReturn(okJson("{\"status\":\"PENDING\"}"))
        .willSetStateTo("done"));

wm.stubFor(get("/payments/1").inScenario("settle")
        .whenScenarioStateIs("done")
        .willReturn(okJson("{\"status\":\"SETTLED\"}")));

// verification - did our code actually call it, and how?
wm.verify(exactly(1), postRequestedFor(urlEqualTo("/audit"))
        .withRequestBody(matchingJsonPath("$.event", equalTo("PAYMENT_SETTLED"))));
Say this

"Stubs let me test the failure paths — timeout, connection reset, malformed payload, 500 from a partner. Those are the branches that actually break in production, and you can't ask a real payment provider to fail on demand."

The honest caveat they want to hear

Stubs test your handling of a contract you assumed. They can drift from reality. That's exactly the gap contract testing fills — next question.

05Contract testing — the senior differentiator›

In a microservices estate, integration tests are slow and flaky, and stubs silently drift from the real provider. Consumer-driven contract testing closes that gap: the consumer declares what it needs, and the provider's build verifies it still delivers it.

  1. The consumer writes a test against a mock provider; that run generates a pact file describing the expected interactions.
  2. The pact is published to a broker.
  3. The provider's pipeline replays those interactions against the real service.
  4. If the provider breaks the contract, the provider's build fails — before the consumer ever sees it.

"We didn't have contract testing, and the recurring pain was exactly what it solves — a provider changed a field and we found out in UAT. If I were setting up a microservices estate now, Pact plus a broker in both pipelines would be an early move."

06Testing asynchronous APIs›

A POST returns 202 Accepted and the work finishes later. Sleeping is the wrong answer; so is asserting immediately.

// Awaitility - poll a condition with a real timeout, no Thread.sleep
await().atMost(30, SECONDS)
       .pollInterval(2, SECONDS)
       .pollDelay(1, SECONDS)
       .untilAsserted(() ->
           given().spec(spec)
           .when().get("/jobs/{id}", jobId)
           .then().body("status", equalTo("COMPLETED")));

The four async shapes and how each is tested:

  • Polling a status endpoint — Awaitility as above. Assert on the terminal state, and also that it doesn't sit in PENDING past the SLA.
  • Webhook callback — stand up a WireMock endpoint as the callback target, then verify() it was called with the right payload.
  • Message queue — publish, then consume from the output topic with a bounded timeout; assert on the message, not on a database side-effect if you can avoid it.
  • Eventual DB state — poll the query, never a fixed sleep, and always assert the absence of the old value too.
Follow-up

"How do you stop async tests being flaky?" Unique test data per run so a slow previous run can't be mistaken for this one, a generous but bounded timeout, and an assertion on the terminal state rather than an intermediate one.

Three things worth raising unprompted:

  • Cache the token per suite, not per test, and refresh on expiry — not on a timer you guessed.
  • Test the authorisation matrix, not just authentication. For each endpoint × role: allowed, forbidden (403), or not-found-by-design (404 to avoid leaking existence). This is where real security bugs live.
  • Never commit secrets. Read from environment variables in CI; the properties file holds the key name, not the value.
Follow-up

"Difference between preemptive and challenged basic auth?" Preemptive sends the Authorization header on the first request. Non-preemptive waits for a 401 and then retries — which doubles the request count and breaks against servers that don't challenge.

08Test data: the problem that actually breaks API suites›

Most "flaky API tests" are really test-data collisions. Four strategies, roughly in order of preference:

  • Create what you need, per test, via API. Self-contained, parallel-safe, and it exercises the create path as a bonus.
  • Unique identifiers always — suffix emails and references with a UUID or timestamp so two runs never touch the same record.
  • Clean up in teardown, and make cleanup idempotent so a failure mid-test doesn't poison the next run.
  • Seeded reference data for things you can't create (a product catalogue) — read-only, never mutated by tests.

A builder keeps the intent visible and the noise hidden:

public static Booking.BookingBuilder aBooking() {
    return Booking.builder()
            .firstname("Test")
            .lastname("User-" + UUID.randomUUID().toString().substring(0, 8))
            .totalprice(100)
            .depositpaid(true)
            .bookingdates(new BookingDates("2026-10-01", "2026-10-05"));
}

// each test states only what it cares about
Booking highValue = aBooking().totalprice(50_000).build();
Booking noDeposit = aBooking().depositpaid(false).build();
Say this

"Shared fixtures are the thing that stops you parallelising. Every test creating its own data costs a few hundred milliseconds and buys you the ability to run the suite forty ways at once."

Field assertions check what you thought of. A schema checks the shape — a field vanishing, a type flipping from number to string, a required field going null, an enum gaining a value.

Follow-up worth pre-empting

"Where do the schemas come from?" Ideally generated from the provider's OpenAPI spec and refreshed in CI, not hand-written and left to rot. A hand-maintained schema that nobody updates is worse than none, because it fails for the wrong reason and gets muted.

11Debugging an API test that fails only in CI›

A structured answer, which is what's actually being scored:

  1. Get the real request. log().ifValidationFails() or a logging filter — then reproduce it as a curl command. Half the time the difference is a header.
  2. Compare environments. Base URI, credentials, feature flags, data. CI usually points somewhere subtly different.
  3. Check for data collision. Does it fail only when run with the rest of the suite? Then it's shared state, not the endpoint.
  4. Check rate limiting. A 429 under parallel load looks exactly like flakiness.
  5. Check timing. CI machines are slower; an async operation that finished locally may not have there.
  6. Correlate with server logs via the correlation ID from the filter.
Say this

"The first thing I do is turn the failing request into a curl I can paste into a terminal. Once it reproduces outside the framework, it's an ordinary bug rather than a test mystery."

Cucumber & BDD

Anyone can write a step definition. The senior questions are all about state, parallelism and whether you should be using it at all. Weight your prep accordingly.

01Gherkin, and the parts people get wrong› 
Feature: Booking cancellation
  As a customer
  I want to cancel a booking
  So that I am not charged for a stay I will not take

  Background:
    Given I am authenticated as a customer
    And a confirmed booking exists

  @smoke @cancellation
  Scenario: Cancelling inside the free window is refunded in full
    When I cancel the booking 5 days before check-in
    Then the booking status is "CANCELLED"
    And a refund of 100% is issued

  @regression
  Scenario Outline: Refund depends on how late the cancellation is
    When I cancel the booking <days> days before check-in
    Then a refund of <percent>% is issued

    Examples:
      | days | percent |
      |   10 |     100 |
      |    3 |      50 |
      |    0 |       0 |

  Scenario: Cancellation reasons are recorded
    When I cancel with the following details:
      | reason      | Change of plans |
      | notifyEmail | true            |
    Then the cancellation reason is stored
  • Background runs before every scenario in the file. Keep it to preconditions, never assertions.
  • Scenario Outline + Examples is for the same behaviour with different data. If the rows need different steps, they're different scenarios.
  • Data Table for structured input; Doc String (""") for a blob like a JSON payload.
  • Tags drive both selection and hooks. Keep them few and meaningful.
The thing panels look for

Declarative, not imperative. When I cancel the booking is a behaviour. When I click the "Cancel" button and wait 2 seconds and click "Confirm" is a script with Gherkin punctuation — and it breaks every time the UI moves.

02Sharing state between steps — the question that separates people›

Step definitions live in different classes, but a scenario needs to carry data across them. Static fields are the wrong answer — they break parallel execution exactly the way a static WebDriver does.

The right answer is dependency injection with a scenario-scoped context. Cucumber-JVM ships PicoContainer; Spring and Guice modules also exist.

// One instance per scenario, created and discarded by PicoContainer.
public class ScenarioContext {

    private final Map<String, Object> data = new HashMap<>();

    public void set(String key, Object value) { data.put(key, value); }

    @SuppressWarnings("unchecked")
    public <T> T get(String key, Class<T> type) {
        return (T) data.get(key);
    }
}

// Constructor injection - Pico wires this automatically
public class BookingSteps {

    private final ScenarioContext context;
    private final BookingApi api;

    public BookingSteps(ScenarioContext context, BookingApi api) {
        this.context = context;
        this.api = api;
    }

    @Given("a confirmed booking exists")
    public void aConfirmedBookingExists() {
        Booking booking = api.create(aBooking().build());
        context.set("bookingId", booking.getId());
    }

    @When("I cancel the booking {int} days before check-in")
    public void iCancelTheBooking(int days) {
        Integer id = context.get("bookingId", Integer.class);
        context.set("response", api.cancel(id, days));
    }
}
Say this

"Each step class takes the context through its constructor and PicoContainer gives every scenario a fresh instance. No statics, so scenarios can't leak into each other and the suite parallelises safely."

Follow-up

"Why not just a static Map?" Because with parallel execution two scenarios on different threads read and write the same map — one overwrites the other's booking id and you get failures that move around between runs. Same class of bug as a static WebDriver.

03Hooks, and their order› 
public class Hooks {

    @Before(order = 0)                  // lower order runs FIRST for @Before
    public void loadConfig() { }

    @Before(order = 10)
    public void startDriver() { }

    @Before("@api")                     // tagged - only for scenarios tagged @api
    public void authenticate() { }

    @BeforeStep
    public void beforeEachStep() { }

    @AfterStep
    public void screenshotEachStep(Scenario scenario) {
        if (scenario.isFailed()) { /* attach */ }
    }

    @After(order = 10)                  // higher order runs FIRST for @After
    public void attachFailureEvidence(Scenario scenario) {
        if (scenario.isFailed()) {
            scenario.attach(screenshotBytes(), "image/png", scenario.getName());
            scenario.log("Correlation id: " + context.get("correlationId", String.class));
        }
    }

    @After(order = 0)                   // ...so teardown runs LAST
    public void quitDriver() { }
}
The detail they check

@Before runs in ascending order; @After runs in descending order. Get it backwards and your screenshot hook fires after the browser has already quit — producing a null driver and a swallowed exception instead of evidence.

Scenario gives you isFailed(), getName(), getSourceTagNames(), attach() and log() — that's how evidence gets into the report.

05Custom parameter types — cleaner than regex soup›

Built-in: {int}, {float}, {word}, {string}, {} (anonymous). You can register your own so steps read in domain language and arrive typed.

06BDD anti-patterns — name these unprompted›
  • Imperative steps. Click-by-click Gherkin. The feature file becomes a brittle script nobody business-side reads.
  • Gherkin as a test-case management tool. Scenarios written after the code, by QA alone, for QA alone. That's not BDD — it's a slower JUnit with extra layers.
  • Shared mutable state between scenarios, so order matters and parallelism is impossible.
  • Over-using Scenario Outline as a data-driven loop. Twelve rows of boundary values belong in a unit or API test, not in living documentation.
  • Conjunction steps — Given I log in and go to the cart and add an item. Split them, or push the setup into a single higher-level step.
  • Technical vocabulary in Gherkin — "the API returns 201". Say "the booking is created"; the status code belongs in the step definition.
  • UI-only BDD. The same behaviours are usually cheaper and steadier driven at the API layer.
07"When is Cucumber not worth it?" — have this answer ready›

This is the single best question to have a confident, non-defensive answer for, because most candidates either defend BDD reflexively or trash it.

Say this

"The value of Gherkin is a shared language with people who don't read code. If the BA and the product owner are genuinely reading and shaping those scenarios — three amigos, before the code — it earns its keep. If QA writes the features alone, after the fact, and nobody else opens them, then you've paid for an extra indirection layer, a glue-code maintenance burden and slower refactoring, and bought nothing. In that situation I'd argue for plain JUnit or TestNG with well-named tests."

The costs to be able to name: an extra layer between test and code, step-definition ambiguity as the suite grows, harder IDE navigation and refactoring, slower onboarding, and reporting that has to be rebuilt on top.

Don't say

"BDD gives better reports." It does produce readable reports, but that's a side effect — leading with it tells the interviewer you're using a collaboration tool as a reporting tool, which is exactly the anti-pattern above.

    config/      qa.properties, uat.properties

The rule that keeps it maintainable: a step definition should be three lines — pull values out of the context, call a service or page object, assert. Any logic longer than that belongs in the layer below, where it's reusable and testable.

Ambiguous step definitions

As a suite grows, two regexes eventually match the same step and Cucumber fails with DuplicateStepDefinitionException or an ambiguous-match error. Prevent it by scoping glue packages per runner and keeping step wording specific rather than generic (I cancel the booking, not I click {string}).

The round most people ramble through

Design round

"How would you test X?" has no right answer, so it's scored on structure. Having one repeatable frame turns the hardest round into the most predictable one.

The frame: C-R-I-S-P

Five moves, roughly ten minutes. Say the headings out loud as you go — interviewers are taking notes against a rubric, and signposting makes their job easy.

  1. Clarify — spend the first 60–90 seconds asking, not answering. Who uses it? What scale? What's already built? What's the biggest risk to the business? Never start designing immediately — that alone fails the round for a lot of candidates.
  2. Risks — name what would actually hurt: money lost, data corrupted, users locked out, a regulator involved. Everything after this is justified by reference to those.
  3. Identify the layers — walk the pyramid explicitly: unit, component/contract, API/integration, UI journey, non-functional. Say what you'd test at each level and what you deliberately would not.
  4. Specifics — now get concrete. Actual test cases, actual edge cases, actual data. This is where you prove you've done it rather than read about it.
  5. Pipeline & ownership — what runs when, who fixes a red build, what the exit criteria are, how you'd measure whether it's working.
The single best habit

Ask "what's the riskiest part of this for the business?" early. It reframes the whole answer around impact instead of coverage, and it's the question a senior engineer asks that a mid-level one doesn't.

Time management

Ten minutes goes fast. Roughly: 1.5 clarify, 1 risks, 2 layers, 4 specifics, 1.5 pipeline. If you're running out, cut specifics, never the pipeline — ending on "and here's how it runs and who owns it" lands much better than trailing off mid test-case-list.

Prompt 01classic

How would you test a URL shortener?

The most-asked design question in SDET interviews. Ten minutes.

What a strong answer covers

Clarify: public or internal? custom aliases allowed? expiry? analytics? expected scale — thousands or billions? Is the short code guessable-by-design or must it be unpredictable?

Risks: collisions (two long URLs, one code), redirect to a malicious site, enumeration of other people's links, unavailability of the redirect path (the read path matters far more than the write path).

Layers:

  • Unit — the encoding function: is it deterministic, what's the alphabet, how long is the code, does it avoid ambiguous characters?
  • API — create returns 201 + code; expand returns 301/302 + Location; idempotency of creating the same URL twice; invalid URL rejected; expired code returns 410 not 404.
  • Data — collision behaviour under concurrent creates for the same URL.
  • UI — one happy journey. That's all the UI is worth here.
  • Non-functional — redirect latency under load, cache behaviour, what happens when the database is down (does the cache still serve?).

Specifics worth naming: very long URL, URL with query string and fragment, unicode/IDN domains, javascript: and data: schemes (should be rejected), already-shortened URL (redirect loop), case sensitivity of the code, trailing slash, concurrent creates racing for the same code.

Pipeline: API suite on every PR since there's barely any UI; load test on the redirect path pre-release; a synthetic monitor hitting a known code in production, because a shortener that stops redirecting is an outage for everyone who ever shared a link.

The line that lands

"The write path is used once per link; the read path is used forever. I'd weight testing and monitoring heavily toward redirects."

Prompt 02money

Design the test strategy for a payment checkout flow

What a strong answer covers

Clarify: which payment methods? own PSP integration or hosted page? do we store card data (PCI scope)? refunds and partial refunds? multi-currency? 3-D Secure?

Risks: double-charging, charging the wrong amount, order created without payment, payment taken without an order, refund failures, PCI exposure. Every one is money or a regulator.

Layers: unit on amount/tax/rounding maths; contract tests against the PSP; stubbed PSP (WireMock) for the failure matrix — declined, insufficient funds, timeout, connection reset, duplicate webhook, out-of-order webhook; API tests for idempotency keys; a small number of end-to-end journeys against the PSP's sandbox; reconciliation checks between order state and payment state.

Specifics: double-click submit; browser back after payment; session expiry mid-payment; webhook arriving before the redirect; webhook arriving twice; refund exceeding the original; currency rounding (0.005); 3-D Secure abandoned halfway.

The senior move

"Idempotency is the centre of this. I'd test that submitting the same payment twice with the same idempotency key charges once, and that a replayed webhook doesn't create a second order. Double-charging is the failure that ends up in the press."

Pipeline: stubbed suite on every PR (fast, deterministic); sandbox end-to-end nightly; reconciliation job monitored in production.

Prompt 03microservices

You have 30 microservices and end-to-end tests are too slow and too flaky. What do you do?

What a strong answer covers

This is really asking whether you understand the test pyramid in a distributed system, and whether you'll say the unpopular thing.

  • Diagnose first. What proportion of failures are real defects vs environment vs data vs timing? Without that number every proposal is a guess.
  • Push down. Most end-to-end tests exist because nobody trusts the layers below. Replace them with contract tests (Pact) between each consumer/provider pair, so a breaking change fails the provider's build.
  • Keep a thin end-to-end layer — a handful of critical business journeys, not a regression suite. Ten good ones beat four hundred.
  • Isolate — each service tested against stubbed dependencies for its own behaviour, with Testcontainers for its own database.
  • Fix the environment. Shared, long-lived, manually-seeded environments cause most of the flakiness. Ephemeral environments per pipeline run, seeded from code.
  • Observability — correlation IDs through every test request so a failure points at a service instead of a screen.
  • Shift right — synthetic monitoring and canary releases catch what pre-prod can't.
Say this

"I'd expect to end up with fewer end-to-end tests, not more. The goal isn't a bigger suite — it's moving each check to the cheapest layer that can still catch the defect."

Prompt 05infra

How would you test a file-upload feature?

What a strong answer covers

Deceptively deep — it's a security question wearing a functional costume.

  • Functional: supported types, size at and just over the limit, empty file, zero-byte vs whitespace-only, very long filename, unicode and emoji filenames, duplicate names, concurrent uploads of the same name.
  • Security: an executable renamed to .jpg (is the check on extension or on magic bytes?); path traversal in the filename (../../etc/passwd); a zip bomb; an SVG containing script; oversized file bypassing client-side validation by posting straight to the API.
  • Integrity: checksum the file on the way out and compare — upload then download and diff, don't just assert a 200.
  • Resilience: connection dropped mid-upload; resume behaviour; storage backend unavailable; quota exceeded.
  • Non-functional: upload time for a large file; many concurrent uploads; cleanup of orphaned temp files.
The point that marks seniority

"Client-side validation isn't a control — I'd bypass the UI entirely and post the payload straight to the endpoint. If the server accepts a 2GB executable because the JavaScript was the only thing checking, that's the actual finding."

Prompt 06judgement

You join a team with no automated tests and a two-week release cycle. First 60 days?

What a strong answer covers

Scored on sequencing and pragmatism, not ambition.

  • Days 1–10 — understand before building. Where do defects actually escape? What does release day look like? What's manually regression-tested every cycle, and how long does it take? That list is your backlog, ordered by pain.
  • Days 10–20 — a thin vertical slice. One critical journey automated, running in CI, visible to the team. Proves the toolchain and buys credibility.
  • Days 20–40 — go where the value is. API tests for the highest-risk services first; they're faster to write and steadier than UI. Automate the manual regression checklist in pain order.
  • Days 40–60 — make it the team's, not yours. Automation in the definition of done, devs writing tests, a shared dashboard, and a flaky-test policy before flakiness appears.
The trap in this question

Announcing a big framework build in week one. The strong answer establishes the pain, ships something small that runs in CI, and only then scales — and says so explicitly.

01

A generic retry helper with exponential backoff

"Write something that retries a flaky operation." Extremely common, and it tests generics plus functional interfaces.

Show solution
public final class Retry {

    private Retry() { }

    public static <T> T withBackoff(Supplier<T> action,
                                    Predicate<T> isAcceptable,
                                    int maxAttempts,
                                    Duration initialDelay) {

        if (maxAttempts < 1) throw new IllegalArgumentException("maxAttempts must be >= 1");

        long delayMs = initialDelay.toMillis();
        RuntimeException last = null;

        for (int attempt = 1; attempt <= maxAttempts; attempt++) {
            try {
                T result = action.get();
                if (isAcceptable.test(result)) {
                    return result;
                }
                last = new IllegalStateException("Unacceptable result: " + result);
            } catch (RuntimeException e) {
                last = e;
            }

            if (attempt < maxAttempts) {
                sleep(delayMs);
                delayMs *= 2;                       // exponential
            }
        }
        throw new IllegalStateException(
                "Failed after " + maxAttempts + " attempts", last);
    }

    private static void sleep(long ms) {
        try {
            Thread.sleep(ms);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();      // restore the flag - do not swallow
            throw new IllegalStateException("Interrupted while retrying", e);
        }
    }
}

// usage
Response r = Retry.withBackoff(
        () -> given().spec(spec).get("/jobs/" + id),
        resp -> resp.statusCode() == 200,
        5, Duration.ofMillis(200));

The three things being marked: generics done properly (<T>, Supplier, Predicate); restoring the interrupt flag rather than swallowing InterruptedException — almost nobody does this and it's a real bug; and chaining the last failure as the cause so the stack trace is diagnosable.

Follow-up: "Add jitter." Multiply the delay by a random factor between 0.5 and 1.5 so parallel clients don't retry in lockstep and stampede the service.

02

Poll until a condition is true, with a timeout

Essentially "write Awaitility". Tests whether you reach for Thread.sleep.

Show solution
public static <T> T until(Supplier<T> probe,
                          Predicate<T> condition,
                          Duration timeout,
                          Duration interval) {

    long deadline = System.nanoTime() + timeout.toNanos();
    T last = null;

    while (System.nanoTime() < deadline) {
        last = probe.get();
        if (condition.test(last)) {
            return last;
        }
        sleep(interval.toMillis());
    }
    throw new AssertionError(
            "Condition not met within " + timeout + ". Last value: " + last);
}

Why this one stays a while: a for loop suits a counted loop — you know how many times it runs. This one runs until a clock runs out, so there's nothing to count and a while reads more honestly. Same for reading a file line by line in problem 05. Everywhere the loop is counted or index-based, prefer for.

Details that matter: use System.nanoTime(), not currentTimeMillis() — the latter jumps if the clock is adjusted. Keep the last observed value and put it in the failure message; "condition not met" alone is useless in a CI log.

Follow-up: "Why not while(true) with a counter?" A count of attempts isn't a time bound — if each probe takes 3 seconds, ten attempts is 30 seconds, not the 5 you intended.

03

Flatten a nested map into dot-notation keys

{a={b={c=1}}} → {a.b.c=1}. Recursion plus generics; very common for JSON comparison utilities.

Show solution
public static Map<String, Object> flatten(Map<String, Object> source) {
    Map<String, Object> out = new LinkedHashMap<>();
    flattenInto(source, "", out);
    return out;
}

@SuppressWarnings("unchecked")
private static void flattenInto(Map<String, Object> source,
                                String prefix,
                                Map<String, Object> out) {

    for (Map.Entry<String, Object> e : source.entrySet()) {
        String key = prefix.isEmpty() ? e.getKey() : prefix + "." + e.getKey();
        Object value = e.getValue();

        if (value instanceof Map) {
            flattenInto((Map<String, Object>) value, key, out);

        } else if (value instanceof List) {
            List<Object> list = (List<Object>) value;
            for (int i = 0; i < list.size(); i++) {
                Object item = list.get(i);
                String indexed = key + "[" + i + "]";
                if (item instanceof Map) {
                    flattenInto((Map<String, Object>) item, indexed, out);
                } else {
                    out.put(indexed, item);
                }
            }
        } else {
            out.put(key, value);        // includes null - deliberately kept
        }
    }
}

Edge cases to volunteer: empty nested map (produces no entry — is that right?), null values, arrays of arrays, and a key that already contains a dot.

04

Diff two maps and report what changed

The natural follow-on from 03 — and the core of any "compare expected vs actual payload" utility.

Show solution
public static List<String> diff(Map<String, Object> expected,
                                Map<String, Object> actual) {

    List<String> differences = new ArrayList<>();

    Set<String> allKeys = new LinkedHashSet<>(expected.keySet());
    allKeys.addAll(actual.keySet());

    for (String key : allKeys) {
        boolean inExpected = expected.containsKey(key);
        boolean inActual   = actual.containsKey(key);

        if (!inActual) {
            differences.add("MISSING  " + key + " (expected " + expected.get(key) + ")");
        } else if (!inExpected) {
            differences.add("EXTRA    " + key + " = " + actual.get(key));
        } else if (!Objects.equals(expected.get(key), actual.get(key))) {
            differences.add("CHANGED  " + key
                    + ": expected " + expected.get(key)
                    + " but was "   + actual.get(key));
        }
    }
    return differences;
}

Why Objects.equals: it null-safes both sides. expected.get(k).equals(...) throws the moment a legitimate null appears.

Follow-up: "How would you ignore volatile fields like createdAt or generated ids?" Take a Set<String> ignoredKeys (or a list of regex patterns) and skip them. That's exactly what real payload-comparison utilities need, and saying it unprompted shows you've built one.

05

Read a CSV into a list of maps

Test-data plumbing. Simple — the marks are in the edge cases.

Show solution
public static List<Map<String, String>> readCsv(Path file) throws IOException {

    try (BufferedReader reader = Files.newBufferedReader(file, StandardCharsets.UTF_8)) {

        String headerLine = reader.readLine();
        if (headerLine == null) {
            return List.of();                        // empty file, not an exception
        }
        String[] headers = headerLine.split(",", -1);

        List<Map<String, String>> rows = new ArrayList<>();
        String line;
        while ((line = reader.readLine()) != null) {
            if (line.isBlank()) continue;

            String[] cells = line.split(",", -1);    // -1 keeps trailing empties
            Map<String, String> row = new LinkedHashMap<>();
            for (int i = 0; i < headers.length; i++) {
                row.put(headers[i].trim(), i < cells.length ? cells[i].trim() : "");
            }
            rows.add(row);
        }
        return rows;
    }
}

The detail interviewers probe: split(",", -1). Without the limit, Java drops trailing empty strings, so a,b,, silently becomes two columns and your row map is short.

An LRU cache

A dev-crossover classic. There's a two-line Java answer and a from-scratch answer — know both.

Show solution
// The Java answer: LinkedHashMap in access-order mode
public class LruCache<K, V> extends LinkedHashMap<K, V> {

    private final int capacity;

    public LruCache(int capacity) {
        super(16, 0.75f, true);        // true = ACCESS order, not insertion order
        this.capacity = capacity;
    }

    @Override
    protected boolean removeEldestEntry(Map.Entry<K, V> eldest) {
        return size() > capacity;
    }
}

The from-scratch answer, if they ask: a HashMap from key to node, plus a doubly-linked list. Get moves the node to the head; put inserts at the head and evicts the tail when over capacity. Both operations O(1) — and O(1) is the whole point of the question.

Follow-up: "Make it thread-safe." Wrap with Collections.synchronizedMap, or use Caffeine/Guava — and say why you'd take the library: correct eviction, TTL, and stats, none of which you want to hand-write.

Merge overlapping intervals

A genuine algorithm question that shows up in SDET loops — and maps neatly onto booking/scheduling domains.

Show solution
public static List<int[]> merge(List<int[]> intervals) {
    if (intervals.isEmpty()) return List.of();

    List<int[]> sorted = new ArrayList<>(intervals);
    sorted.sort(Comparator.comparingInt(a -> a[0]));      // sort by start

    List<int[]> merged = new ArrayList<>();
    int[] current = sorted.get(0);
    merged.add(current);

    for (int[] next : sorted) {
        if (next[0] <= current[1]) {                       // overlap
            current[1] = Math.max(current[1], next[1]);    // extend
        } else {
            current = next;
            merged.add(current);
        }
    }
    return merged;
}
O(n log n) from the sort · O(n) extra space

Edge cases: touching but not overlapping ([1,3] and [3,5] — do they merge? ask), a single interval, one interval fully containing another, and whether the input may be mutated (this version mutates; say so).

01equals / hashCode, and what breaks›

Equal objects must have equal hashCodes. The reverse isn't required. Override equals() and forget hashCode() and your object goes into one bucket but is looked up in another — HashSet.contains() returns false for an object that is equal, silently.

Directly relevant to test code: any deduplication, any distinct(), any assertion comparing collections of POJOs depends on it.

02HashMap internals — the four numbers›

Default capacity 16, load factor 0.75 so it resizes at 12 entries. A bucket chain converts to a red-black tree at 8 (once the table is at least 64 buckets) and reverts at 6. Collisions land in the same bucket and are separated by equals().

ConcurrentHashMap is the parallel-safe version: per-bin locking, no nulls, reads never block.

04Waits — the one Selenium answer that must be perfect›

Implicit — global, every findElement, presence only. Explicit — one element, one condition, polls every 500ms. Fluent — explicit plus custom polling and ignored exceptions.

Never mix them

The explicit wait calls findElement internally while polling, and each of those inherits the implicit timeout — so a 10-second explicit wait under a 20-second implicit wait can block far longer than either number. public final class DriverFactory {

    private static final ThreadLocal<WebDriver> DRIVER = new ThreadLocal<>();

    public static void init() {
        ChromeOptions options = new ChromeOptions();
        options.addArguments("--disable-dev-shm-usage");
        WebDriver driver = new ChromeDriver(options);
        driver.manage().timeouts().implicitlyWait(Duration.ZERO);
        DRIVER.set(driver);
    }

    public static WebDriver get() { return DRIVER.get(); }

    public static void quit() {
        if (DRIVER.get() != null) {
            DRIVER.get().quit();     // quit(), not close()
            DRIVER.remove();         // pooled threads are reused
        }
    }
}

The two details that get checked: quit() rather than close() (close leaves the session alive and leaks driver processes), and remove() so a reused thread doesn't inherit a dead reference.
